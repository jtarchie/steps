| # | Requirement | Fixture | Red observed |
|---|---|---|---|
| 1 | Steps inside `in_parallel:` run concurrently; `limit:` bounds how many at once | `examples/in-parallel-basic.yml` | `PROBE EXIT 2` — `field in_parallel not found in type config.Step` |
| 2 | `fail_fast: false` tolerates a failing child; all siblings still run | `examples/in-parallel-fail-fast.yml` | `PROBE EXIT 2` — `field in_parallel not found in type config.Step` |
| 3 | Nesting works: `in_parallel` inside `in_parallel` | `examples/in-parallel-nested.yml` | `PROBE EXIT 2` — `field in_parallel not found in type config.Step` |
| 4 | Routing scope: a child's `to:` target routes to another child within the same branch | `examples/in-parallel-routing.yml` | `PROBE EXIT 2` — `field in_parallel not found in type config.Step` |

All four fail identically: the YAML decoder's `KnownFields(true)` rejects `in_parallel` as an unknown field on `config.Step`. This is exactly the RED state we want — once the `InParallel *InParallelSpec` field is added to `Step`, these fixtures will load and (once execution is wired) pass.

## Fixture design notes

- **No execution ordering assertions on in_parallel children**: Children run in goroutines and finish non-deterministically. `assert.execution` at the job level asserts exact ordered step names, which would be flaky. Instead, every fixture uses step-level `assert.stdout` on each child — each child self-verifies its own output, immune to interleaving.
- **No `assert:` on the in_parallel wrapper itself**: The plan rejects assert on in_parallel (same as try). The fixtures put assert on children only.
- **No `# steps-test: skip`**: All fixtures are designed to pass `steps test` once the feature is built. None are skipped.
- **All fixtures use `limit:` or `fail_fast:` where applicable** to exercise those fields, even though the fixture can't directly verify the limit/fail_fast behavior — the fields being accepted by the parser is part of what's being tested.
