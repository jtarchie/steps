# Implementation Plan: 000 — `attempts:` and `timeout:` on every step

## Overview

This plan implements two operational limits on all four step kinds (get/task/put/agent):
- **`attempts:`** (get/task/put only; agent already has this) — retry count for retrying unmodified commands
- **`timeout:`** (all four) — wall-clock deadline per attempt

Key constraints from the proposal:
- Hook firing (`on_failure`/`on_error`) fires once after final attempt exhausted, not per attempt
- Fix interaction: `fix:` runs once per exhausted attempt (separate budget)
- Assert interaction: only final attempt's output/exit code is evaluated
- Timeout classification as `errored` (not `failed`)
- Both fields are NOT hashed (operational limits, like `assert:`)
- Visibility: log "attempt 2/3" markers per retry

### 2. `internal/pipeline/pipeline.go`

**Changes for Get Steps (runGetStep):**
- Wrap each resource `check`/`in` call with timeout context (derived from step.Timeout)
- On `context.DeadlineExceeded`, classify as errored (not failed)
- Retry loop around version fetching: attempt count from step.Attempts (default 1)
  - Log "attempt N/M" before each retry
  - Same linear backoff as agent attempts (retry.Do)
  - Only fire hooks after final attempt exhausted, not after intermediate failures

**Changes for Task Steps (executeTask):**
- Extract timeout from resolved task (step.Timeout overrides task.Timeout)
- Wrap `runner.RunCaptureFullLimitedStreamed()` (or whichever variant) with timeout context
- Implement retry loop (new code):
  - Call `retry.Do(ctx, step.Attempts, ...)` with timeout-derived context
  - Log "attempt N/M" before each retry
  - On failure (including timeout), proceed to fix: if present
  - Fix runs once per exhausted attempt, not once total
  - Assert evaluated only on final attempt's output/code
  - After all attempts exhausted, record outcome and return error for hook dispatch
  
- Hook firing: currently `executeTask` doesn't directly fire hooks (pipeline.runSteps does that). Verify hook dispatch happens only after all attempts exhausted.

**Changes for Put Steps (executePut):**
- Extract timeout from step.Timeout
- Wrap resource `out` call with timeout context
- Retry loop:
  - Call `retry.Do(ctx, step.Attempts, ...)` with timeout-derived context
  - Log "attempt N/M" before each retry
  - After all attempts exhausted, return error for hook dispatch

**Helper function:**
- `parseTimeout(s string) (time.Duration, error)` — reusable parser, nil-safe
- Used by config.LoadConfig, pipeline step runners, and agent's own timeout handling

**Tests needed:**

- Timeout semantics: per-attempt, deadline for command wall-clock time

## Edge Cases & Open Questions

### 1. Fix timeout interaction (not fully specified in proposal)
- **Current assumption**: fix runs once per exhausted attempt, with its own `Timeout` if set
- **Alternative**: fix shares parent task's timeout budget?
- **Recommendation**: fix has separate timeout (FixSpec.Timeout), so fixing doesn't starve retries

### 2. Get step timeout semantics
- Does `attempts: 3` on get mean retry check/in separately, or the entire get-version-fetch?
- **Recommendation**: retry entire sequence (check then in), backoff between full cycles

### 3. Global/job-level timeout default (proposal: "recommend starting explicit-only")
- **For now**: no global default; every step opts in explicitly
- **Future**: could add to job: or pipeline: block without hashing impact (operational)

### 4. Timeout on get steps with version: every
- A get with version: every fans out multiple chains; should each retry independently?
- **Recommendation**: yes, each version attempt can retry up to attempts: times

### 5. Agent timeout vs agent attempts interaction
- Agent already has attempts (per-step retry of conversation)
- Adding timeout (per-attempt): is it `min(step.Timeout, agentStepTimeout)`?
- **Recommendation**: step.Timeout overrides agentStepTimeout if set; if not set, use agentStepTimeout (10m)

### 6. Assertion behavior under retries
- Proposal: "assert should evaluate only the *final* attempt's captured output/exit code"
- Task captures (stdout/stderr/exitCode) — must discard intermediate attempts?
- **Recommendation**: pipeline stores latest attempt's output; assert runs only on final
