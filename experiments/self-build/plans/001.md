# Implementation Plan: 001 — `try:` tolerated failure

## Overview

Add a `try:` wrapper step that wraps a single inner step and always reports
success to the plan walker, even when the inner step fails. The inner step's
hooks fire normally; `to:` routing sees the real outcome; `assert:` on the
inner step still gates; output clearly flags "step failed (tried, continuing)".

The wrapper composes with `attempts:`/`timeout:` on the inner step (retry a few
times, then shrug) and with `fix:` on a task (attempt repair, then tolerate).

Key constraints from the proposal (story 001):
- Routing uses the inner step's real outcome, not the swallowed one
- Inner step hooks fire normally
- `assert:` on the inner step evaluates the real outcome (a silently-broken
  tried step must still fail `steps test`)
- Output visibility: "step failed (tried, continuing)"
- Composability with `attempts:`/`timeout:`/`fix:`
- `try:` itself can carry `to:`, hooks, `attempts:`, `timeout:`, `max_visits:`
- `try:` makes its chain uncacheable (like put/agent — wrapper changes behavior)
- Hooks on the try step: fire on the swallowed (always-success) outcome

**New validation: `validateTrySteps`** — called from `config.go:validate()`:
```go
func (c *Config) validateTrySteps() error {
    for _, job := range c.Jobs {
        err := job.visitSteps(func(label string, step *Step) error {
            if step.Try == nil {
                return nil
            }
            // A try: must wrap an inner step with a recognized kind.
            innerKind, ok := step.Try.Kind()
            if !ok {
                return fmt.Errorf("%s: try: wraps an unrecognized or empty step", label)
            }
            // try: may not wrap a get step — gets fan out per version, which
            // has no coherent meaning inside a tolerated wrapper.
            if innerKind == StepKindGet {
                return fmt.Errorf("%s: try: cannot wrap a get step", label)
            }
            // try: may not carry kind-specific fields that collide with the
            // inner step's own: get/task/put/agent must be unset.
            fields := step.kindFieldsSet()
            if len(fields) > 1 { // "try" + something else
                return fmt.Errorf("%s: try: is a wrapper — do not also set get/task/put/agent", label)
            }
            return nil
        })
        if err != nil {
            return err
        }
    }
    return nil
}
```

**New function: `runTryStep`** — the core execution logic:
```go
func runTryStep(ctx context.Context, cfg *config.Config, jobName string, i int, step config.Step, bw workspace.BuildWorkspace, st *store.Store, parentHash string, handoff *agent.Handoff) (string, stepDisposition, nonGetOutcome, error) {
    // Hash the try wrapper node.
    hash, err := hashTryStep(cfg, step, parentHash)
    if err != nil {
        return "", stepRan, nonGetOutcome{}, err
    }

    node := merkle.Node{Hash: hash, ParentHash: parentHash, Kind: merkle.NodeKindTry, StepIndex: i, Content: ...}

    // Dispatch the inner step. If it's a get, handle specially (get has its
    // own fan-out; see runSteps). For task/put/agent/try, use dispatchNonGetStep.
    innerHash, innerDisposition, innerOutcome, innerErr := dispatchNonGetStep(ctx, cfg, jobName, i, *step.Try, bw, st, nil, parentHash, handoff)

    if innerErr != nil {
        fmt.Printf("try: %s failed (tried, continuing)\n", executedStepName(*step.Try))
        slog.Info("job.try", "job", jobName, "step", executedStepName(*step.Try), "outcome", "tolerated")
    }

    // Record the try node as succeeded regardless of inner outcome.
    recCtx := context.WithoutCancel(ctx)
    _ = st.RecordNode(recCtx, nodeRecord(node), jobName, "succeeded", nil, innerErr)

    // The plan walker always sees success — return nil error.
    // But the real outcome is threaded through nonGetOutcome so that
    // to: routing on the try step sees the truth.
    return hash, stepRan, innerOutcome, nil
}
```

That would skip the inner step even when wrapped in try — which is wrong because try changes the semantics. Since `try:` makes the chain unskippable, the inner task can't be cached anyway (the parent hash includes the try wrapper, so it's a different chain). Actually, `dispatchNonGetStep` for a task step checks `skippable[hash]`. If we pass nil for skippable, the inner step always runs. That's what we want for try — the try wrapper itself is always unskippable, so the inner step should always execute.

But there's a subtlety: the inner step's own caching should still work IF the try step itself were somehow skippable (it's not). So passing nil skippable is fine.

Actually, let me reconsider. The try wrapper is its own plan step. `runSteps` sees it as a non-get step. It calls `dispatchNonGetStep` which dispatches to `runTryStep`. Inside `runTryStep`, we dispatch the inner step (which may be task/put/agent/try). For a task inner step, we call `dispatchNonGetStep` with `skippable=nil` (always run). This is correct.

But wait — the inner step's parent hash. If the inner step is hashed with the try step's parent hash (not the try step's own hash), then caching works at the inner step level — but since the try step makes the chain unskippable anyway, caching is irrelevant.

**Revised `runTryStep`:**

```go

    // Build and record the try wrapper node.
    content, err := merkle.TryNodeContent(cfg, *step.Try, parentHash)
    if err != nil {
        return "", stepRan, nonGetOutcome{}, err
    }
    hash, err := merkle.HashNode(merkle.NodeKindTry, content, parentHash)
    if err != nil {
        return "", stepRan, nonGetOutcome{}, err
    }

    node := merkle.Node{Hash: hash, ParentHash: parentHash, Kind: merkle.NodeKindTry, StepIndex: i, Content: content}

    // Run the inner step — no caching (nil skippable). Inner steps that are
    // themselves try steps recurse here. A get inside try is rejected at
    // LoadConfig time, so we don't handle it.

    }

    // Record the try node as succeeded regardless.
    recCtx := context.WithoutCancel(ctx)
    _ = st.RecordNode(recCtx, nodeRecord(node), jobName, "succeeded", nil, innerErr)

```

**But wait** — there's a problem with `innerHash`. The inner step computed its hash against `parentHash` (the try step's parent), not against the try step's hash. This means the merkle chain is flat: `parentHash → innerHash`, with the try node being a "ghost" that doesn't appear in the chain. This is wrong — the try node SHOULD be in the chain.

Let me reconsider. The correct chain structure should be:
`parentHash → tryHash → innerHash`

So the inner step's parent should be `tryHash`, not `parentHash`. That way the chain properly reflects the try wrapper.

But `dispatchNonGetStep` for the inner step computes its hash from the parentHash passed in. So I need to change the approach: instead of calling `dispatchNonGetStep` directly (which uses parentHash for hashing), I need to either:
1. Call `dispatchNonGetStep` with `parentHash = hash` (the try node's hash), so the inner step chains under the try node
2. Or compute the try node's hash from the inner step's content + parentHash, then record both

Option 1 is simpler and correct. The try node's hash becomes the inner step's parent:
```go
innerHash, innerDisposition, innerOutcome, innerErr := dispatchNonGetStep(ctx, cfg, jobName, i, *step.Try, bw, st, nil, hash, handoff)
```

This means the merkle chain is: `parentHash → hash (try) → innerHash (task/put/agent/try)`. The try node AND the inner step's node are both recorded. The try node is always "succeeded"; the inner step's node is recorded by `dispatchNonGetStep` as whatever it actually was (succeeded or failed).

Wait, but `dispatchNonGetStep` IS going to record the inner step's node (via `runTaskStep`/`runPutStep`/`agent.RunStep`). That node will be recorded with its real outcome. Then the try wrapper records its own node as succeeded. This means the store has TWO nodes for one step — the inner (real) node and the try wrapper node. The inner node may be "failed" while the try node is "succeeded" — which is exactly right: the inner step failed, the try wrapper tolerated it.

But this creates a problem for `buildSkippableIndex` — which uses parentHash chaining. The inner step chains under `hash` (try), and the next step after try chains under `innerHash`. The `skiptable` map keys `innerHash` → false (unskippable because there's a put/agent in the chain). The try step itself is also unskippable. So downstream steps after the inner step will correctly NOT be skipped.

Actually, the chain structure matters more for planning. `PlanChains` needs to handle try too. Let me think about this...

For planning, `planNonGetNode` currently handles task/put/agent. Adding try:
```go
case config.StepKindTry:

    return node, true, err // always unskippable
```

Where `tryNode` builds the try wrapper's content and hash. Then `planSteps` continues with the next step (after try) using the try node's hash as parent. This mirrors the runtime behavior where `runTryStep` returns the inner step's hash (since the next step chains after the inner step, not after the try wrapper).

Wait, this is getting complicated. Let me simplify.

**Simplified approach: try re-uses the inner step's hash as its own.**

Instead of being a separate node in the chain, the try wrapper modifies the inner step's content (adding a "try": true marker) and uses the inner step's computed hash. This way:
- The chain is: `parentHash → (inner content + "try":true) → nextStep`
- The try wrapper doesn't create a separate node — it IS the inner node, with "try" folded in
- `dispatchNonGetStep` is called with the try step's step (which has Try set), and it delegates to the inner step's dispatch but with modified content

This is conceptually cleaner and avoids double-recording. The try wrapper is a content modifier, not a separate step.

But this doesn't work with the current architecture, where `Step.Kind()` determines dispatch. A try step has `Kind() == StepKindTry`, not `StepKindTask`.

OK, let me step back. The simplest approach that works with the existing architecture:

**`runTryStep` calls `runNonGetStep` for the inner step (which handles recording + hooks), then records the try node as succeeded.**

The chain structure: 
- `parentHash → tryHash (recorded as succeeded) → next step chains under tryHash`
- The inner step's node is recorded independently by `runNonGetStep` (as failed/succeeded)
- The inner step's hash is NOT in the chain — the chain goes through the try node

Actually, this is also problematic because `runNonGetStep` records the inner step's node with `parentHash` as its parent. If the try step passes `tryHash` as parentHash, then the inner step chains under the try node. But the chain also needs to continue: the step after try should chain under the try node (or the inner node?).

Let me just go with: the try wrapper chains under its parentHash (the previous step), and the next step chains under tryHash. The inner step is NOT part of the chain — it's executed inside try and its node is recorded but its hash is not the chain's next link.

```
parentHash → tryHash → nextStepHash
                 ↘ innerHash (recorded independently, not in plan chain)
```

This makes planning simple: `tryNode` returns the try wrapper's hash, and `planSteps` continues with the next step using tryHash as parentHash. The inner step is hashed into the try node's content (so changing the inner step changes tryHash), but the inner step doesn't create its own chain node.

At runtime, `runTryStep`:
1. Dispatches the inner step (with nil skippable, parentHash = tryHash for recording purposes)
2. Inner step records its own node as failed/succeeded
3. Try step records its own node as succeeded
4. Returns tryHash (not innerHash) for the chain

This is clean. Let me revise the plan with this approach.

**New function: `runTryStep`**:
```go
func runTryStep(ctx context.Context, cfg *config.Config, jobName string, i int, step config.Step, bw workspace.BuildWorkspace, st *store.Store, parentHash string, handoff *agent.Handoff) (string, nonGetOutcome, error) {
    content, err := merkle.TryNodeContent(cfg, *step.Try)
    if err != nil {
        return "", nonGetOutcome{}, err
    }
    content = merkle.WithHooksAndRouting(cfg, step, content) // try's own hooks/routing

    hash, err := merkle.HashNode(merkle.NodeKindTry, content, parentHash)
    if err != nil {
        return "", nonGetOutcome{}, err
    }

    node := merkle.Node{Hash: hash, ParentHash: parentHash, Kind: merkle.NodeKindTry, StepIndex: i, Content: content}

    fmt.Printf("try: %s\n", executedStepName(*step.Try))
    slog.Debug("job.step", "job", jobName, "index", i, "kind", "try", "inner", executedStepName(*step.Try))

    // Run the inner step — no caching (nil skippable). The inner step's
    // own recording (success or failure) happens inside dispatchNonGetStep.
    _, _, innerNo, innerErr := dispatchNonGetStep(ctx, cfg, jobName, i, *step.Try, bw, st, nil, hash, handoff)

    // Inner hooks already fired. Wrap the outcome.
    if innerErr != nil {
        fmt.Printf("try: %s failed (tried, continuing)\n", executedStepName(*step.Try))
        slog.Info("job.try", "job", jobName, "step", executedStepName(*step.Try), "outcome", "tolerated")
    }

    // Record the try wrapper as succeeded.
    recCtx := context.WithoutCancel(ctx)
    _ = st.RecordNode(recCtx, nodeRecord(node), jobName, "succeeded", nil, innerErr)

    // Return the real outcome for routing (to: on try routes on truth).
    return hash, innerNo, nil // nil error = plan continues
}
```

**Key design points:**
- Inner step gets `parentHash = hash` (try's hash) — the inner node chains under the try wrapper
- Inner step always runs (nil skippable)
- Try wrapper is always recorded as "succeeded"
- Real outcome threaded through `nonGetOutcome` for `to:` routing
- The plan continues with nil error always

## Design Decisions and Tradeoffs

### Q1: Should `try:` create its own merkle node?

**Decision: Yes.** The try wrapper folds the inner step's content under a `"try"` key and hashes against the chain's parentHash. The inner step's own node is recorded independently (as failed/succeeded) but is NOT part of the plan chain — the chain goes through the try node. This means:
- Removing `try:` from a step changes its hash (correct: behavior changed)
- The inner step's own caching is irrelevant (try is always unskippable)
- The chain structure is `... → tryHash → nextStepHash`, with inner node recorded independently

**Alternative considered:** try as a transparent passthrough (no own node). Rejected: this would mean removing try doesn't invalidate the cache, which is wrong — a step that used to tolerate failure suddenly doesn't.

### Q2: Should `try:` wrapping a `get` step be valid?

**Decision: No.** A get step fans out per version, which has no coherent meaning inside a tolerated wrapper. The story's example shows `try: put:`, which is the primary use case. This can be relaxed later if needed.

### Q3: How should `try:` interact with `assert:` on the inner step?

**Decision: The inner step's assert fires normally.** The story explicitly says: "`steps test`'s `assert:` must check the inner step's real outcome, not the swallowed one." This means the try wrapper does NOT interfere with assert — it runs the inner step normally, and if the inner step has an assert, that assert gates the inner step's outcome. If the inner step's assert makes it a success, try has nothing to swallow. If the inner step fails (even with assert), try swallows it.

### Q4: Should `try:` be valid as a hook body?

**Decision: Yes.** A hook that wraps a task/put/agent in try is useful — e.g., `on_failure: try: { put: slack-notify }`. The inner step's hooks still fire; the try wrapper's hooks fire on the swallowed outcome. Since hooks are already reactions to failure, wrapping one in try is a reasonable pattern.

### Q5: Does the try step's `timeout:` apply to the inner step or the wrapper?

**Decision: The try step's timeout applies to the wrapper (which includes the inner step's execution).** The inner step can have its own timeout. If the inner step times out and the try step also has a timeout, the try step's timeout bounds the total: the inner step's timeout fires first (per attempt), and if retries exhaust the try step's timeout, the try step itself errors.
