# Implementation Plan: 002 — `in_parallel:` run steps concurrently (keystone)

## Overview

Add an `in_parallel:` step type that runs multiple child steps concurrently.
The wrapper occupies a single position in the plan; each child runs its
own hooks, records its own outcome, and participates in artifact flow.
The wrapper aggregates outcomes: on `fail_fast: true`, the first child
failure cancels siblings; otherwise all children run to completion.
Duplicate output/artifact names across branches are rejected at load.

This is a **new `StepKind`** — a wrapper containing multiple child steps,
analogous to `try:` (which wraps one step). Both Query 1 (switch sites)
and Query 2 (field reads on wrappers) apply.

Key design decisions from the story:
- `limit:` bounds max in flight (default: unbounded)
- `fail_fast: true` cancels siblings on first failure; `context` cancellation
  must be honored cleanly by in-flight agent steps
- **Naming collisions**: duplicate output/artifact names across branches
  are a **load-time error** (not runtime or silent last-write-wins)
- **Log interleaving**: concurrent output carries a per-branch label prefix
- **Routing scope**: `to:`/`verdicts:` targets inside a branch stay within
  that branch; a branch cannot route to a sibling or outside the block
- **Nesting**: `in_parallel` inside `in_parallel` works from day one
- **Workspace safety**: documented hazard of concurrent writers sharing one
  workspace; docs point users at `strategy: copy` or `btrfs`

## Data model

### New types in `internal/config/step.go`

```go
// InParallelSpec is the in_parallel: step — run several steps concurrently
// with an optional concurrency limit and fail-fast cancellation.
type InParallelSpec struct {
    Limit    int    `yaml:"limit,omitempty"`
    FailFast bool   `yaml:"fail_fast,omitempty"`
    Steps    []Step `yaml:"steps"`
}
```

New field on `Step`:
```go
InParallel *InParallelSpec `yaml:"in_parallel,omitempty"`
```

New `StepKind` constant:
```go
StepKindInParallel StepKind = "in_parallel"
```

`Step.Kind()` extended: `{StepKindInParallel, s.InParallel != nil}` goes after `Try` in the candidate list.

`kindFieldsSet()` extended: add `{"in_parallel", ...}` when `s.InParallel != nil`.

`visitStepTree()` extended: after `step.Try` recursion, add recursion into `step.InParallel.Steps` (each child, labeled with branch index).

### YAML shape handled

`InParallelSpec` needs a custom `UnmarshalYAML` (or uses gopkg.in/yaml.v3's automatic decode) that accepts:
```yaml
in_parallel:
  limit: 2          # optional, int >= 1
  fail_fast: true   # optional, bool
  steps:            # required, non-empty sequence
    - get: repo
    - task: lint
      run: golangci-lint run
```

A bare `in_parallel:` (nil pointer) is rejected by `validateStepKinds` (zero kinds). An `in_parallel:` with an empty or missing `steps:` is rejected by a new validation.

### 2. `internal/config/route.go` — Routing scope and segment validation

**`stepName()`:** add `case StepKindInParallel:` returning `""`.

**`rejectRoutingOnGet()`:** add check: `to:`/`max_visits:`/`verdicts:` on an in_parallel child with `Get != ""` is still rejected (the existing check for get handles this since it fires on each child individually via visitStepTree).

**`validateSegment()`:** When building the `pos` map (step name → segment position), in_parallel's `stepName` returns `""`, so it won't be in the map. That's correct — it's not a routable target. But children inside the branch: their `to:` targets must resolve within their own branch. This requires extending `validateStepRouting` (or adding a new branch-scoped validator) that:
1. For each in_parallel step, validates routing within each branch independently
2. A child cannot route to a sibling branch's step
3. A child cannot route to a step outside the in_parallel block

**`validateStepRouting()`:** The `inner := step.Unwrap()` pattern works for try (one inner step). For in_parallel, we need a different approach — iterate children and validate each one's routing within the branch.

**`validatePlanSegments()`:** No structural change needed — in_parallel is non-get so it belongs to a segment. Children are within the same segment. The key question: when a child routes to another child within the same branch, does the segment walker see it? Since the segment is a flat list of plan indices, an in_parallel block adds N children but only 1 plan index (the wrapper). The children are NOT individual plan entries — they're sub-steps of the wrapper.

**Decision:** For routing purposes, children of in_parallel form their own mini-segment (branch). Routing within a branch is validated against that branch's steps only. Cross-branch routing is rejected. This requires a new validation function `validateInParallelRouting` that walks each branch's steps and checks `to:` targets resolve within the branch.

This also means `max_visits` on the wrapper bounds how many times the ENTIRE in_parallel block may execute in a backward route. Individual children cannot carry `max_visits` (rejected by validateInParallelSteps).

**Tests needed:**
- `TestInParallelRoutingWithinBranch` — child routes to another child in same branch → accepted
- `TestInParallelRoutingCrossBranch` — child routes to a sibling branch → rejected
- `TestInParallelRoutingOutsideBlock` — child routes to a step after the in_parallel block → rejected
- `TestInParallelVerdictRoutingWithinBranch` — agent child with verdicts routes within branch → accepted

### 7. `internal/config/hooks.go` — Allow in_parallel in hooks

**`validateHookStep()`:** Add `StepKindInParallel` to the allowed kinds (it's a container, the children are validated recursively). `get` inside an in_parallel hook is still valid because the check for `StepKindGet` is on the child, which is visited by visitStepTree.

Wait — actually, `validateHookStep` rejects `StepKindGet` for a direct hook body. An in_parallel hook containing a get step: the hook's body is in_parallel, not get, so it passes. But a get inside a hook (even nested in in_parallel) is still wrong — a get fans the plan per version, which has no meaning in a hook. So `validateHookStep`'s recursive walk via `visitStepTree` must also check children of in_parallel for get steps.

**Decision:** When validating hook steps, recurse into in_parallel children and reject any get found.

## Open questions / risks

1. **Get steps as children**: The story does not explicitly address whether get steps inside in_parallel are allowed. They ARE shown in the YAML example (`get: repo`, `get: rules`). However, a get step fans the rest of the plan per version — inside in_parallel, there IS no "rest of the plan" after the get (the in_parallel block ends). So get steps inside in_parallel would need to be treated as simple fetches (no fan-out). This needs a design decision. **Likely answer**: get steps inside in_parallel fetch the latest version and publish the artifact; no fan-out. `version: every` inside in_parallel is rejected at load.

2. **Get-fan interaction with in_parallel at plan level**: If an in_parallel block containing a get is preceded by a get with `version: every`, the fan-out iterates the entire in_parallel block per version. That's the existing runSteps behavior (get fans the remainder, and in_parallel is part of the remainder). No special handling needed — the entire block re-executes per version, which is correct.

3. **Hook execution for in_parallel children**: Each child runs its own hooks. The wrapper's hooks fire after all children complete, on the aggregated outcome. This mirrors the try: pattern where the wrapper's hooks fire on the swallowed/tolerated outcome.

4. **Merkle caching**: in_parallel is always unskippable (concurrent execution is non-deterministic by nature). Children within the block are never cached (nil skippable map). This is the same conservative approach as try:.

5. **Output streaming**: The `[branch N]` prefix must be applied at the point output is written, not buffered. This might require a labeled writer that prepends the prefix to each line. The simplest approach: use `fmt.Printf` with the prefix inside the goroutine. Since multiple goroutines write concurrently, lines may interleave but each line carries its branch label.
