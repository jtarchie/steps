## Edge cases verified

- **Bare try** (`try: {}`): rejected by validateTrySteps ("unrecognized or empty step") — tested in try_test.go
- **try + get**: rejected ("cannot wrap a get step") — tested
- **try + another kind**: rejected ("is a wrapper") — tested
- **try in hook wrapping get**: rejected transitively — tested
- **Nested try**: accepted, works in merkle and config — tested
- **try with trigger/version/params**: caught by existing validateStepFieldPlacement checks (trigger/version only on get, params only on put — try is neither)
- **try with `to:` routing**: stepName delegates to inner name, unskippableReason returns "try step" — routing sees real outcome via innerNo

parentHash → tryHash (recorded "succeeded") → nextStepHash

## Non-blocking observations

1. **validateStepFieldPlacement not modified** (handoff watch_out #4).
   The handoff says trigger/version/params "pass load" on try — but in practice
   they ARE caught by existing checks: `trigger && !isGet` fires because
   `isGet` is false for a try-only step. Same for params. No harm either way.

2. **tryNode() doesn't set Resource** (handoff watch_out #1). All other node
   builders (taskNode, putNode, agentNode) set Resource. `tryNode` does not.
   This means `steps plan` shows an empty Name for try nodes. Runtime
   `runTryStep` sets it via `executedStepName`. Minor UX inconsistency.

3. **validateStepKinds error message** still says "get/task/put/agent" without
   "try". A user setting try+task gets the message from validateTrySteps first
   (clear), but if validateTrySteps ever moves after validateStepKinds the
   secondary message would be confusing.

4. **stepContentMap / hookContentMap duplication** (handoff watch_out #2).
   Both dispatch on task/put/agent independently; only the try case is shared
   via TryNodeContent. If a new step kind is added, both need updating.

5. **Test coverage gaps**: no e2e test for try+put or try+agent (only
   try+task); no runtime test for `to:` routing on a try step; no runtime
   test for try wrapper's own hooks (only merkle hash test). The mechanism
   looks correct in each case — these are coverage gaps, not bugs.

6. **Docs claim about `on_success` on try wrapper**: docs say "Hooks on the
   try wrapper observe the swallowed outcome (always success), so `on_success`
   always fires and `on_failure` never fires." This is true: the try node is
   always recorded "succeeded" so `runHooks` would fire `on_success` hooks.
   But there's no runtime test confirming this.

None of these observations block correctness. The feature ships as designed.
