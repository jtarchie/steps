# internal/shell

- **A container's exit status is DATA; only "there was no container" is an error.** The pipeline separates the step saying no from the machinery breaking by asking `shell.IsExitError`, and every answer used to come from `*exec.ExitError`, which has no constructor and can only describe a child of this process. Three outcomes must keep their meanings: a command that ran and exited nonzero is a `*shell.ExitError`; a DAEMON refusing the start (an unknown image) keeps the **125** `docker run` reports, because docs/infra.md documents that number and an agent is shown it as tool output; and a container that started and then DIED is neither — it never accepted a command, so it stays an infrastructure error, and misreading it lets a guard treat an unusable image as the guard answering no and skip the work it gates with nothing red. **A container that dies at birth is only detectable by WAITING** (`dockerapi.SettleFor`, `dockerSettleBound`): an image whose ENTRYPOINT swallows the keepalive is still running at the instant the start returns. The old shape got this for free because spawning `docker inspect` WAS the delay; asking directly is fast enough to ask too early. **The wait is a bet, so it has a backstop that is not**: a loaded daemon lets a doomed container outlive the 300ms window (measured: it flaked a validation run with the daemon's bare "is not running", naming neither image nor reason). `dockerSession.diagnose` therefore asks the daemon whenever a command could not be PREPARED, and gives a dead container the same postmortem — "exited immediately" if it never served a command, "stopped while the step was using it" if it had. Both stay plain infrastructure errors with the daemon's own error in the chain. A test that needs the window gone sets `dockerSettleBound` to zero; a test that needs THE container asks the session for its id rather than listing by pid label, which assumed the previous test's container was already gone.
