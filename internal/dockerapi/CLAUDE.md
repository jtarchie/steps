# internal/dockerapi

- **Containers are created over the engine API, not by spawning `docker`.** `internal/dockerapi` is the ONLY package that holds an engine client, and it is a leaf (`internal/shell` imports it; nothing else does). It exists because a CLI answers two questions a library does not, and both fail TOTALLY rather than partially when unanswered: WHICH DAEMON — `client.FromEnv` reads `DOCKER_HOST` and stops, while docker goes on to `DOCKER_CONTEXT`, then the `currentContext` in `config.json`, then the store under `contexts/meta/<sha256 of the name>`, which is what `docker context use colima` writes and how a great many machines are configured; and WHICH CREDENTIALS — the daemon cannot read anybody's keychain, so a login travels on the pull request, and the ONLY one sent is what a caller attached for that exact reference with `WithPullLogin` (a `registry-image` resource's own, #276). The operator's `config.json`, `credsStore` and `credHelpers` are deliberately never read for credentials: a pipeline's reach is what its file says, on any machine. **A new call that needs either answer goes through `dockerapi`, never through `client.FromEnv`.** Two consequences worth knowing: nothing needs a `docker` binary on PATH any more (a daemonless, docker-less orchestrator runs PLACED containerized steps fine, which is why `ValidateDockerCLI` is gone), and an `ssh://` `DOCKER_HOST` is REFUSED rather than dialled: a `docker+ssh://` worker already forwards a remote daemon's socket, so the mapping is the one place an ssh daemon is spelled.
- **A container mounts named volumes only.** `CreateContainer` and `CreateHolder` refuse a `Bind` whose source is a path (`volumesOnly`), before the daemon is asked: a tree reaches a container through volumes a venue fills (steps#246), and a bind mount names a path on the DAEMON's filesystem, which an unshared VM answers with an empty directory rather than an error. This guard is what keeps a new caller from bringing one back.
- **Every engine client is built by `connect` (trace.go), which is what names and filters its spans.** The client traces itself and names a span by raw path, so each container, volume and image was a new span name in a backend; `routeOf` takes the ids out. Two requests are filtered rather than renamed: the version ping, and `SettleFor`'s wait, whose deadline is the healthy answer and was recorded as an error on every container (99% of all error spans, measured). A new route with an id in it needs a `collections` entry; a new wait-until-timeout call needs `untracedKey` on its context.
