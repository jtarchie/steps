# internal/dockerapi

- **Containers are created over the engine API, not by spawning `docker`.** `internal/dockerapi` is the ONLY package that holds an engine client, and it is a leaf (`internal/shell` imports it; nothing else does). It exists because a CLI answers two questions a library does not, and both fail TOTALLY rather than partially when unanswered: WHICH DAEMON — `client.FromEnv` reads `DOCKER_HOST` and stops, while docker goes on to `DOCKER_CONTEXT`, then the `currentContext` in `config.json`, then the store under `contexts/meta/<sha256 of the name>`, which is what `docker context use colima` writes and how a great many machines are configured; and WHICH CREDENTIALS — the daemon cannot read the operator's keychain, so the client resolves a login (`credHelpers`, then `credsStore`, then `auths`, with Docker Hub filed under a legacy v1 URL) and sends it on the request, without which every pull from a private registry 401s on a machine where `docker pull` works. **A new call that needs either answer goes through `dockerapi`, never through `client.FromEnv`.** Two consequences worth knowing: nothing needs a `docker` binary on PATH any more (a daemonless, docker-less orchestrator runs PLACED containerized steps fine, which is why `ValidateDockerCLI` is gone), and an `ssh://` `DOCKER_HOST` is REFUSED rather than dialled: a `docker+ssh://` worker already forwards a remote daemon's socket, so the mapping is the one place an ssh daemon is spelled.
- **A container mounts named volumes only.** `CreateContainer` and `CreateHolder` refuse a `Bind` whose source is a path (`volumesOnly`), before the daemon is asked: a tree reaches a container through volumes a venue fills (steps#246), and a bind mount names a path on the DAEMON's filesystem, which an unshared VM answers with an empty directory rather than an error. This guard is what keeps a new caller from bringing one back.
