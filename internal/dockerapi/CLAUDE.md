# internal/dockerapi

- **Containers are created over the engine API, not by spawning `docker`.** `internal/dockerapi` is the ONLY package that holds an engine client, and it is a leaf (`internal/shell` imports it; nothing else does). It exists because a CLI answers two questions a library does not, and both fail TOTALLY rather than partially when unanswered: WHICH DAEMON — `client.FromEnv` reads `DOCKER_HOST` and stops, while docker goes on to `DOCKER_CONTEXT`, then the `currentContext` in `config.json`, then the store under `contexts/meta/<sha256 of the name>`, which is what `docker context use colima` writes and how a great many machines are configured; and WHICH CREDENTIALS — the daemon cannot read the operator's keychain, so the client resolves a login (`credHelpers`, then `credsStore`, then `auths`, with Docker Hub filed under a legacy v1 URL) and sends it on the request, without which every pull from a private registry 401s on a machine where `docker pull` works. **A new call that needs either answer goes through `dockerapi`, never through `client.FromEnv`.** Two consequences worth knowing: nothing needs a `docker` binary on PATH any more (a daemonless, docker-less orchestrator runs PLACED containerized steps fine, which is why `ValidateDockerCLI` is gone), and an `ssh://` `DOCKER_HOST` is REFUSED rather than dialled — not because ssh is hard, but because a remote daemon resolves a bind mount against its own filesystem, finds nothing, and creates an empty directory instead of failing; `--worker ssh://...` is the mechanism that actually sends the tree.
