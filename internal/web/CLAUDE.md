# internal/web

`internal/web` (echo + `html/template` + one CSS file + a vendored htmx, all `go:embed`ed) serves the browser UI over the same state the CLI writes. The rules that keep this from becoming a second product:

- **web sits above pipeline**, like trigger: it reaches execution only through `pipeline.RunJob`, never into agent/resource/merkle. depguard enforces it.
- **Recording is the runner's job.** `RunJob` attaches a store-backed bus when the caller supplied none, so EVERY run persists its events, not just watched ones. A run started from a terminal and one started from the browser leave the same record.
- **The live view and the post-hoc view are the SAME rendering.** SSE polls `run_events` by sequence number rather than subscribing to the in-process bus — that is what lets the UI show runs another process started, and what stops a live view and a replayed one from drifting. What travels over that stream is the `step` template's own HTML, rendered server-side from the same assembled view the page renders, and htmx's `hx-sse` extension swaps it in: `hx-swap-oob="outerMorph"` for a row the page already drew, `hx-swap-oob="beforeend:#transcript"` for one that opened after it was drawn (an out-of-band swap at an id that is not there is dropped, and an append of a row that IS there draws it twice — `flushEvents` picks by asking whether the READER has the row: its first event came at or before the sequence they resumed from, or this connection has since sent it. Asking instead whether a `step.started` arrived in the flush was the same question for every step that has one, and wrong for the step that does not: a row swallowed by a chain skip is opened by its `step.skipped`, so it was swapped over an id nothing had drawn and vanished). The unit sent is a ROOT step, not an event, because a row shows facts no single event carries: a container's rollup changes when its third child finishes and nothing publishes an event on the container. **The fold stays open for the life of the connection** (`runFolder`, seeded once with the history the reader already has, then fed each batch): re-reading the run per flush was the obvious way to render a delta and wrong twice over — it inherited the page's `runEventLimit`, so past 5,000 events a flush found no touched step in its truncated view and wrote NOTHING while holding the socket open and re-arming the idle deadline (a frozen transcript on a live connection, nothing logged), and it cost a whole-run fold per tick per watcher: measured on the same 800-event fixture, 1,069,672 bytes and 14,753 allocations per tick became 90,360 and 1,410. The stream also PAGES rather than reading once, and drains until a flush adds nothing, so a run that recorded more than one batch between ticks is not delivered a batch at a time and then closed. **This replaced a second renderer in the browser** — ~700 lines rebuilding every row, turn and JSON payload from JSON events, including a ~250-line mirror of `jsonview.go` whose own comment conceded it could not match — and the standing rule it kept breaking ("anything the server draws for a finished step, the stream has to draw too") had been enforced one field at a time: `data-toggle`, the `open`/`container` classes, the agent's answer, the "stopped early" badge, the worker name, an absolute node link. Each was found by a reader who had to reload. `TestStreamDrawsTheSameMarkupThePageDoes` now asserts the whole thing at once, and there is nothing left for the two paths to disagree about. Reconnects resume from `Last-Event-ID` (every frame is stamped), falling back to the `?after=` the page was rendered with; a flush is ONE message however many rows it changed, because a browser resends the id of the last message it APPLIED: split across several, a flush could be resumed from the middle of itself, and a row appended in a message that never arrived is gone for the rest of the run — every later flush renders it as a swap onto an id the page never drew. What the stream does NOT draw is everything outside the transcript — the run's own status, the spend and placement tables — which is what the closing reload on `done` is for, and it doubles as the backstop for a lost frame.
- **Every page that shows changing state refreshes itself, and htmx is what does it.** A region carries `hx-get="{{.Nav.URL}}" hx-trigger="every[!document.hidden] 2500ms" hx-select="#itself" hx-swap="outerMorph"` and names the rest of the page's changing parts — the metaline, the queue, `#nav-tabs` — in `hx-select-oob`: the page is its own API, one GET re-renders it, and only the named elements are swapped. Three details are load-bearing and none is a default. **`outerMorph`** reconciles the DOM instead of replacing it, which is what lets a region holding a form (the approvals reason box, a question's answer) be refreshed at all, keeps focus and selection, and makes an unchanged region a no-op; a plain `outerHTML` swap empties an input every 2.5 seconds — and note that an `hx-select-oob` entry with no style of its own gets `outerHTML`, so the first stateful widget put in one of those regions has to ask for `#id:outerMorph`. **The trigger's SPELLING is load-bearing and was wrong once**, which is why `TestLiveRegionsAreDrivenByHtmx` asserts it on every polling page: htmx 4 parses the modifiers with HCON, where a bare token holding a dot is a nested PATH, so `every 2.5s` became `{"2":{"5s":true}}`, the interval was read as the first non-`name` key, integer-like keys sort first, and every open tab polled at **2 milliseconds**. A filter is likewise only a filter when it is ATTACHED to the event name — `every 2.5s [!document.hidden]` parsed the bracket as junk and dropped the guard that stops a forgotten background tab polling forever. And nothing a swap replaces may carry view state: the jobs board's list/graph choice lives on `<body data-view>` with CSS, because a `hidden` attribute on the swapped element itself snapped back to the server's answer under a reader who had chosen otherwise. Overlapping polls need no guard of ours, but not for the reason to hand: `hx-sync` defaults to `queue first`, so one overlapping poll is QUEUED and fires the instant the in-flight one lands — serialized, which is what actually kills the stale-response race, rather than dropped. Two things this replaced, and both were the reason for it: the job, approvals, questions, resources and overview pages did not refresh AT ALL (a run triggered while the job page was open appeared only on reload), and the jobs board and runs page each carried a hand-written copy of the poll loop that had already drifted apart. `liveregion_test.go` is the probe that keeps it honest: it renders a page, changes the state behind it, renders again, and fails for every line that appeared outside a region `hx-select`/`hx-select-oob` names — so a new page, or a new stateful section on an old one, fails until htmx is pointed at it. It counts lines rather than setting them, because HTML repeats itself and a set called a whole new run row "already there". htmx is VENDORED into `static/` (4.0.0), never a CDN: this server is expected to run where there is no route to one. **The one page that still polls by hand is `follow.html`**, deliberately: it waits for a queued job to become a run and then NAVIGATES, and htmx 4 ships no `HX-Redirect` — a page whose whole job is to leave is not a swap.
- **A run is a TREE, and the tree is minted, not derived.** `run_events.step_id`/`parent_step_id` carry it (see [../events/CLAUDE.md](../events/CLAUDE.md) for why the merkle chain cannot). `buildRunView` folds events into a flat `Steps` list — still what run-level questions are asked of — and `linkTree` hangs each on its container; the template recurses over `Roots`.
- **Reader state is the client's, and a swap must not take it back.** Morph reconciles a row to what the server drew, so the two things the server cannot know are lost the moment a step changes: which rows the reader folded open, and which row they are on (`j`/`k`). Both are recorded in `layout.html` as the reader makes them and re-applied on `htmx:after:swap`. An expanded JSON payload is handled a third way, declaratively — `htmx-config`'s `morphSkip` names `details[open]`, so a fold the reader opened is left alone while every closed one updates normally.
- **Agent prose is untrusted, and `prose.go` is the boundary.** It is a SECOND goldmark converter, deliberately not `docs.go`'s: that one renders this repo's own embedded docs and may trust them. Raw HTML and `javascript:` are closed by goldmark's defaults; images are rendered inert (a beacon URL in a review is an outbound GET on page open) and heading ids are not generated (an agent must not mint an anchor that collides with `#step-N-name`). The live path no longer touches `innerHTML` at all: it receives markup this package escaped, rather than rebuilding rows in the browser from untrusted step names, command output and model-chosen tool names.
- **The stream's escaping obligation is TWO-part, because the wire is not HTML.** `html/template` covers the markup; `writeFrame` covers the FRAME, and only the second one knows that SSE ends a line on CRLF, CR *or* LF while `html/template` escapes the five HTML metacharacters and not the carriage return. A bare CR in a step's stdout — every progress bar writes them — ended the `data:` line early and everything after it was read as SSE fields, so `\r\revent: done\r\r` on a task's output was a forged run-completion frame that closed the reader's stream and painted the tab red on a job still running. `frameLines` normalizes CRLF and sends a lone CR as `&#13;`. A field added to the `step` template inherits this; a new transport does not.

`internal/events` is the leaf that carries run events here — see [../events/CLAUDE.md](../events/CLAUDE.md).
