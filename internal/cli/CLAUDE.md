# internal/cli

The kong command surface, and the half of the daemon that chooses a store driver and a workspace provider (`daemon.go`, `web_cmd.go`, `db.go`). `internal/web` serves; this package owns what it serves.

- **The daemon HOLDS pipelines; `steps pipeline set` uploads them.** `steps web` takes no pipeline arguments and starts empty: a pipeline arrives over HTTP (`PUT /api/pipelines/<name>`, `internal/web/api.go`) and by nothing else, which is what makes vars per-set rather than process-wide, makes a pipeline's identity a NAME somebody chose rather than a filename, and makes a change happen because somebody asked rather than because a file moved. There is no file watcher and no `--once` (both deleted with #104). The set path is `internal/cli/daemon.go` — the half that chooses a store driver and a workspace provider, implementing `web.Manager`, which `internal/web` deliberately does not do. Three properties are load-bearing. **Validation happens on the machine that will RUN it** (`daemon.accept`: parse, `fileProblems`, `CheckEnvironment`, workspace) and the refusal travels back over HTTP to the terminal that asked — that is the whole reason the transport is not a database row, which would need an ack protocol of its own. **Includes travel as a bundle**: a `run_file:` is pipeline-relative and a daemon has no sibling filesystem, so `set` sends `{source, includes}` and the daemon resolves through `config.Bundle`, which is CLOSED on purpose — an include it was not sent must fail rather than read the daemon's own disk. **The workspace provider is leased** (`internal/scheduler/providers.go`): a set may replace it, and `Close` removes the tree it created, so a run keeps the provider it started with and the old one is closed only once the runs holding it finish. `steps run`/`test`/`validate`/`plan` still take a file path — they are the local commands, and a local command has a file. `steps run --target` (#283) is the exception that proves it: it sends the file to `POST /api/one-offs` (`oneoff.go`), and the daemon serves it UNPOLLED under a name it mints with the `one-off.` prefix (reserved, so a minted name is never one somebody set) and marks it with `pipelines.one_off` before its revision goes current — the COLUMN is what a restart reads, so it restores a one-off unpolled — then the terminal follows it through `remote_runs.go`, the same `followRun` the state-file follow uses, after waiting on the queue row the enqueue answered (`GET /api/pipelines/<p>/queued/<id>`) rather than the newest run, so a row merged into or aborted before its start is answered exactly; `runs trigger --follow` (#294) waits the same way. A run id is minted at CLAIM (`scheduler.resumeAsked`), never at enqueue, which is why the row and not a run id is what a trigger answers. **Finished one-offs are bounded by count, never age** (`--one-off-history`, default 10, 0 keeps all): each time a one-off's queue settles `trimOneOffs` ranks the settled ones by their newest run's end and destroys past the bound, so a running one-off is never counted or reaped, and one with no run (a crash between record and queue) ranks oldest. Concourse keeps `fly execute` builds forever (its build-log reaper walks only job builds); this diverges because a one-off here is a whole served pipeline.
- **One `steps` process per state database, and nothing enforces it.** The `flock`-based single-watcher lock was deleted deliberately (2026-08-23), `steps watch` went in the CLI consolidation (2026-08-30, #89) and `--once` went with #104: `steps web` is the whole long-running mode — it serves, holds the pipelines, polls, and drains the queue all of that fills, and a second one against the same state file is a deployment mistake rather than a supported pairing. What the lock protected is `ResetStaleRunning`, which reads every `running` queue row as an abandoned leftover — true only when nothing else is alive, false when another process is mid-build, where flipping the row lets the job be claimed twice and silently defeats `serial:`/`max_in_flight`. With one daemon there is nothing to pair with, so `web` always owns the queue and always recovers; `--no-watch` went with it, and `--read-only` is unrelated (it withholds the HTTP controls, never the drain). Do not reintroduce a lock, or a second daemon, without asking.
- **`steps web`'s terminal is slog and nothing else** — asked for repeatedly, and repeatedly regressed: its `events.Output` is `Headless` (every writer `io.Discard`, nothing prompts; a step's bytes are already captured into `step_output` and read from the store or the browser), its bus's one observer is `runview.Log` (a step's lifecycle as debug records, a note at its own level because a parked approval's answer command is one an operator acts on), and the daemon's own lines (`web_cmd.go`, `daemon.go`, `internal/trigger`'s poller) are slog calls. `steps run` keeps its plain lines; only the daemon is slog-only. `TestDaemonTerminalIsOnlySlog` holds it. The live view (`runview.Live`, `--progress`) and `runview.Plain` are the other renderers, and `pipeline` imports neither: the CLI names one for every local run (`ProgressFlags.draw`), and a run with none draws nothing. It hands it to `RunJob` through `events.WithRenderer` rather than installing its own bus, because a caller-supplied bus skips `RunJob`'s close-then-prune ordering; it takes step bytes through `events.Output.Step` for its tails and gives a prompt the terminal through `events.Hold`. The rest of the printing rule (`events.Note`, `Observe` vs `Subscribe`, the renderers) is in [internal/events/CLAUDE.md](../events/CLAUDE.md#nothing-below-internalcli-prints).
