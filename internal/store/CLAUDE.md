# internal/store

The state-database contract (`internal/store`, stdlib-only) and its two drivers (`internal/store/sqlite`, `internal/store/postgres`). The foreign-key rule and its four exceptions live in the root [CLAUDE.md](../../CLAUDE.md#working-rules), because they bind every schema change.

## Contract and drivers

**The state database is a contract and two drivers.** `internal/store` is stdlib-only: the row types, the error sentinels, `EncodeVersion`/`DecodeVersion`, the size caps, and the `Store`/`Reader` interfaces. `internal/store/sqlite` and `internal/store/postgres` (pgx through `database/sql`) each hold every connection and every query of their own, and each asserts `var _ store.Store = (*Store)(nil)` so a drifting method is a build error. Only `internal/cli` names a driver — `cli/db.go` is the one scheme switch, and `cli.State` is a resolved `--db` whose `String()` redacts a url's password, so printing one is safe by default; everything else takes the `store.Store` it was handed, and a test that needs a real database opens the sqlite one (depguard says so, per package). Each driver writes its own schema and its own SQL rather than sharing a dialect — so `internal/store` must never learn to open anything. **Postgres answers several connections at once, and sqlite's single writer was carrying invariants nobody wrote down**: a `check_order` from a `MAX` just read, a claim's count of what is already running, a prune's view of what survives. Under READ COMMITTED each is a race, so every Postgres transaction that reads before it writes goes through `write()`, which takes `pg_advisory_xact_lock(classPipeline, pipeline_id)` — a single writer per pipeline again, for exactly those transactions — and `RecordNode` holds `classContent` SHARED against the pipeline-blind `node_content` sweep's EXCLUSIVE, or another pipeline's sweep can delete a row between a node seeing it and referencing it. Both are proven by sabotage (`storetest/concurrency.go`, `postgres/race_test.go`); a new read-then-write in that driver takes the lock. Its tables live in their own schema (`steps`, or the url's `search_path`), never `public`, and every connection's `search_path` is that schema alone, so a same-named table another application owns can never be adopted. Its test server is Postgres 17 from embedded-postgres' binaries (`internal/testpostgres`), started in the package's `TestMain` (and lazily per shard in `./e2e`) with no docker involved, skipped cleanly only when the binaries cannot be had. **`Store` is a composition of sixteen facets and nothing else** — `Meta`, `Runs`, `Cache`, `Blobs`, `Versions`, `Queue`, `Approvals`, `Questions`, `Placements`, `Usage`, `Events`, `Revisions`, `Control`, `Pruning`, `Deliveries`, `Memories` — each declared in the file whose aggregate it names, because those file boundaries already were the aggregates. `facets_test.go` reflects over the interface types and fails if Store's method set is not exactly their union, or if two facets share a method: a method declared straight on `Store` belongs to no aggregate, so no consumer could ask for it by name and a second driver would have no facet to write it under. **A consumer declares the facets it calls, not `store.Store`** — `agent.StepStore` is Usage+Questions+Memories plus the one `SaveNodeTranscript` method it needs from Cache (nodes and the skip index are pipeline's, for every step kind), `trigger.PollStore` is Queue+Versions, `cli`'s read commands take the one or two facets they read. Only code that runs a whole build (`pipeline.RunJob`, `web`) takes the whole thing. The compiler is the enforcement: a call to an undeclared facet does not build. **The behavior tests are the contract's, not the driver's**: `internal/store/storetest` is the conformance suite — `Run(t, open)`, where `open(t, pipelineName)` hands back a handle and two names in one test must reach ONE database. A driver runs the whole thing from a single test (each driver's `conformance_test.go`), so the second driver is proven by the tests the first already passes rather than by tests nobody wrote. Each test is an exported method on an unexported `suite` and `Run` finds them by reflection — a test nobody registered is a test that silently stops running, which is the failure the package exists to prevent, and a method it cannot call fails the suite rather than disappearing from it. What stays in a driver's own package is what measures THAT driver: the `dbstat` footprint, the pragmas, the schema stamp, the read-only file bit, cross-process enqueue, and any test that reaches past the interface into raw SQL. `storetest.TestTheOpenerSharesOneDatabase` is the one holding the opener to its half of the deal — every cross-pipeline scoping test below it passes for free against an opener that hands out a database per name.

## Pipeline scoping

- **A state file holds SEVERAL pipelines, and every row says which one it belongs to.** A daemon keeps all of its in ONE database — `.steps/steps.db` unless `--db <url>` says otherwise (a bare path or `sqlite://<path>`; the scheme switch is `cli.DB`, in the CLI because `internal/store` cannot import its drivers) — while the file-driven commands still default to `.steps/<filename>.db` beside the YAML. Sharing is a STORAGE decision and never a semantic one: `pipelines(id, name, path)` is the parent, every pipeline-scoped table carries `pipeline_id … REFERENCES pipelines(id) ON DELETE CASCADE`, and **the `Store` handle holds the id** — which is why ~60 methods kept their signatures, why a caller cannot forget to scope, and why `steps pipeline rename` is one UPDATE that keeps history where a filename-derived identity made a rename a different pipeline. The run-scoped tables (`run_steps`, `run_events`, `agent_usage`) reach it through `runs` instead, and `run_placements` reaches it that way too while also carrying a `pipeline_id` of its own, because the node it names is a composite reference into `nodes(pipeline_id, hash)`; `node_content` is deliberately global, keyed by a hash OF the content, so its sweep must stay pipeline-blind or the `RESTRICT` fires. **A new query in `internal/store/sqlite` without a `pipeline_id` predicate is a bug, and `tools/sqlscope` fails the build over one** — it reads the scoped tables out of the schema itself, folds `const + literal` concatenations, and refuses any statement on one of them that names no pipeline (a run-scoped table, `run_id REFERENCES runs` with no `pipeline_id`, must name it or reach `runs`, which is why their inserts are `INSERT … SELECT … WHERE EXISTS (run in this pipeline)` and a miss is `ErrNoSuchRun`); the four that are cross-pipeline on purpose are listed in its test with the reason each is safe, and an entry that excuses nothing fails too. Its limit is marked `ponytail:` in the source: it proves the pipeline is NAMED, not that every table in a join is scoped. The sharpest case is the cache: `merkle.HashNode` folds in kind/content/parent but NOT the pipeline, so two pipelines each with a job named `build` over an identical task produce the same hash — unscoped, the second silently skips work it never did. That is why `nodes` is keyed `(pipeline_id, hash)` and `job_runs` `(pipeline_id, job_name, root_hash)`. **`pipelines.current_revision_id` is what a daemon SERVES**, RESTRICTed so retention cannot reap the configuration a restart would rebuild from, and `revision_includes` is why that rebuild works with no YAML anywhere on the box.

## Bounds, retention and the cache

- **The state database is bounded, and both bounds are pipeline settings.** `defaults.version_history:` caps recorded resource versions per resource; `defaults.run_history:` caps runs per job, and reaping a run takes its events, per-step records, agent usage, placements, questions and inputs with it (`internal/store/sqlite/retention.go`, called at the end of every build from `pipeline.RunJob`). Zero means no limit for both, per the convention in [docs/attempts-timeout.md](../../docs/attempts-timeout.md#zero-means-no-limit). `internal/store/sqlite/footprint_test.go` MEASURES the result with sqlite's `dbstat` — a change that grows what a build costs on disk fails there, which is the point.
- **History is bounded by recency; the CACHE is bounded by count, never by age.** `nodes` and `job_runs` are the merkle/chain caches, capped as a multiple of `run_history:` and evicted newest-by-`rowid`. Age is the wrong question for them and was a real bug: a fully-cached poll records no new node, never reaches `recordChainSucceeded`, and publishes its skip events with an EMPTY hash (`reportChainSkipped`), so nothing about a cache HIT refreshes any timestamp — a working pipeline's entries just looked older every poll until an age-based floor swept past them, and the faster it polled the sooner it lost the cache. A count cap cannot do that: a fully-cached pipeline creates no new entries, so nothing is ever evicted.
- **Stored timestamps use `sortableNano`, not `time.RFC3339Nano`.** These columns are ordered and compared as TEXT, and RFC3339Nano TRIMS trailing zeros — so `…:00.5Z` sorts after `…:00.51Z`, and a whole second sorts after every fraction inside it. Retention DELETES by that order, which made it able to reap the newer of two runs in one second. Any new stored timestamp uses the fixed-width layout. That is sqlite's rule; the Postgres driver stores `timestamptz` (truncated to the microsecond it keeps, read back `.UTC()`) and breaks ties with an identity column, which is its answer to both halves of the same problem.

## Schema changes

- **Since v0.1.0 a schema change is a migration, in BOTH drivers, in the same commit.** `schemaVersion` is a migration counter from the version v0.1.0 shipped (`oldestUpgradable`: sqlite 28, Postgres 14); each driver's `migrate.go` holds `migrations`, where step i takes a database from `oldestUpgradable+i` to the next. Bump `schemaVersion`, change the DDL in `schema.go` (still the one place to read the schema: a fresh database gets it directly, never a replay), and append the step. **Steps are APPEND ONLY once on main** — JT's own daemon runs main, so a step there has already run on a real database; a wrong one is fixed by the next. **`TestV010UpgradesToTheFreshSchema` is the guard, one per driver**: it loads `testdata/v0.1.0.sql` (that release's DDL copied from the tag, plus rows — FROZEN, never edited), opens it, and requires the catalog to equal a fresh database's and the rows to survive. Column order is not compared, because `ADD COLUMN` appends while the DDL may place a column anywhere; constraint and index names are. A step that needs data the fixture lacks gets a new fixture beside it, not an edit. **The cache tables (`nodes`, `job_runs`) may be emptied by a step rather than migrated — that costs one cold rebuild; history may not.** sqlite: `upgrade` runs when a writer first opens the file's pools (`acquirePools`, under `poolsMu`, so EVERY writer — `OpenStore`, `OpenAccounts`, `Identity` — gets it; `steps web` with nobody signing in reaches the file first through `Identity`, and a writer that skipped it left the daemon refusing to start), after `VACUUM INTO <file>.v<old>.bak` (owner-only, only the newest kept); the steps and the stamp are one transaction. Postgres: inside `inSchema`'s transaction under the schema advisory lock, so a failed step leaves the schema untouched; it needs the role to own the tables. A read-only open (`OpenReader`, `OpenExisting`) never upgrades — it refuses with which command will. Still refused: older than `oldestUpgradable` (delete the file / `DROP SCHEMA`) and newer than this build. **Without the bump an older database opened fine, lacked a column, and failed every INSERT naming it — and since the run-event sink only warns, the build went GREEN having recorded nothing**; that is why `checkSchemaVersion` refuses rather than tolerates. An empty version-0 sqlite file is stamped rather than refused, having nothing to lose. Postgres keeps its counter in a one-row `schema_version` table and runs its DDL only when that table is ABSENT, so a matching open is one read and needs no `CREATE` privilege.
