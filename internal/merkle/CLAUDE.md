# internal/merkle

**A config field either moves the cache key or is named as not meant to** (`internal/merkle/keyfields_test.go`). It perturbs every leaf of every hashed config type by reflection, so a NEW field that no builder folds in fails the build — the alternative is a cached step reported green having never seen the new configuration. A field left out on purpose is listed with a reason that says where it comes from: `source:` (the code's own doc says so) or `observed:` (nothing does; it was found that way and reported, because folding a field in changes the key for every cached step and that is not a test's call). **Leaving a field out on purpose costs a sentence on the field's own doc comment** — "Never hashed: <why>" — and the table cites it; an exclusion whose only record is the test is one nobody will find when they change the field. Its twin pins the bytes each builder produces with every optional field UNSET, which is the value-gating promise — a pipeline not using a field keeps its cache — and the only thing that catches `> 0` becoming `>= 0`. Probes build a `Config` by hand, so anything the LOADER resolves (an agent's description onto the grant naming it, `system_file:` into `system:`) reads as silent there while being keyed in a real pipeline; the table says so. **A silent field is a question about the PROBE before it is a finding about the key**: `settings:` was reported as unkeyed and recommended for keying on the strength of a probe whose agent was hosted — where `settings:` is refused at load and correctly never folded — while `AgentContentMap` had keyed it as `cli_settings` all along and docs/agents-internals.md said so. A field that exists for only one kind of agent, resource or grant needs a probe of THAT kind (`Agent/cli` is the one that came out of this), and the docs' own "Caching" notes are worth a grep before calling anything a gap.
