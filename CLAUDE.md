# CLAUDE.md: steps Pipeline Runner

Trust these instructions. Only search the codebase if something here is missing or turns out to be wrong — this file is validated, not guessed. Package-specific mechanics live in a `CLAUDE.md` beside the package and load when you work there; this file is the map and the rules that bind everywhere.

## What this repo is

**steps** is a Go CLI that executes Concourse-style YAML pipelines (`resource_types`/`resources`/`jobs`), with an LLM `agent` step type built in alongside conventional `get`/`task`/`put` steps. Resources are discovered/fetched via templated shell commands (or MCP); `agent` steps call an LLM with tool calling. All state is cached in SQLite (WAL mode) via content-addressed (merkle) hashing, so unchanged steps are skipped on rerun.

- **The state database is bounded by `run_history:`/`version_history:`, its cache by count never age, it holds several pipelines with every query scoped by `pipeline_id` (`tools/sqlscope` enforces), timestamps use `sortableNano`, and since v0.1.0 a schema change bumps `schemaVersion` AND appends a migration step in both drivers** — [internal/store/CLAUDE.md](internal/store/CLAUDE.md).
- **The daemon HOLDS pipelines; `steps pipeline set` uploads them**, validated on the machine that runs them, includes as a closed bundle, workspace provider leased — [internal/cli/CLAUDE.md](internal/cli/CLAUDE.md).
- **One `steps` process per state database, and nothing enforces it.** Do not reintroduce a lock, or a second daemon, without asking — why: [internal/cli/CLAUDE.md](internal/cli/CLAUDE.md).
- **Containers are created over the engine API, not by spawning `docker`**; a call needing daemon or credential resolution goes through `internal/dockerapi`, never `client.FromEnv` — [internal/dockerapi/CLAUDE.md](internal/dockerapi/CLAUDE.md).
- **A container's exit status is DATA; only "there was no container" is an error** (125 for a refused start, a container dead at birth is infrastructure) — [internal/shell/CLAUDE.md](internal/shell/CLAUDE.md).
- **Nothing below `internal/cli` prints** (forbidigo refuses `fmt.Print*`/`os.Stdout`/`os.Stderr` elsewhere); machinery speaks through `events.Note` and `events.Stdout/Stderr(ctx)`, and `steps web`'s terminal is slog only — [internal/events/CLAUDE.md](internal/events/CLAUDE.md#nothing-below-internalcli-prints), [internal/cli/CLAUDE.md](internal/cli/CLAUDE.md).
- **No CI configured**: there is no `.github/`, no CONTRIBUTING.md. `Taskfile.yml` (go-task) is the entire validation pipeline — run it locally exactly as documented before considering any change done.

## Working rules

- **Unspecified behavior → ask "What would Concourse do?"** steps is a Concourse-shaped DSL; when a semantic isn't pinned down by this repo (what a field means at an edge, ordering, when a step is skipped, how a version is picked, what counts as a change), the default answer is whatever Concourse does. Research it thoroughly first — Concourse docs, its source, real pipeline behavior — then come back with the finding AND the open questions for the user. Do not invent a semantic and do not guess in silence; a divergence from Concourse is a deliberate decision the user makes, not a side effect of an implementation.
- **Foreign key constraints are required.** Every SQLite column in `internal/store/sqlite` that references another table's key declares a `REFERENCES` constraint with an explicit `ON DELETE` action. `PRAGMA foreign_keys=ON` is set on the connection, so a missing constraint is a silently-orphaned row, not a saved line. A relationship that genuinely cannot be a foreign key needs a comment naming why. **Four columns are such exceptions, all pinned by a negative assertion in `footprint_test.go` so they stay deliberate**: `nodes.parent_hash`, because a container step (`do:`/`in_parallel:`/`race:`/`across:`/`ensemble:`/`try:`) records its node AFTER the children that hashed under it, so the child legitimately precedes the parent; and `job_runs.root_hash`, because a chain ending in a container has a leaf hash no node describes, and cascading the skip index off node retention would silently re-run work that succeeded; and `run_events.parent_step_id`, for the same shape of reason as `nodes.parent_hash`; and `agent_usage.step_id`, because `run_events.step_id` is not a key. Adding either of the first two makes every block step fail to record.
- **TDD, outside-in.** Write the test first. Start with the happy-path end-to-end test — the one that runs a real pipeline through `run()` and asserts the outcome a user would see — and only then work downward into the narrower tests (package-level, then unit) for the branches, errors, and edge cases the e2e pass doesn't reach. An e2e that passes is the proof the feature exists; the tests below it are the proof it holds up. A feature whose first test is a unit test is a feature nobody has run.
- **Fixes are features: they land with a test, and the test is proven by sabotage.** This rule exists because it was violated, expensively: a batch of review fixes landed test-free across several commits, and a later audit showed that deleting any of them shipped green through this whole sequence. Before committing a fix, break the fix (edit it back, in memory — never `git checkout --`, which also destroys the uncommitted fix), run the test, watch it fail, restore. A test that survives its own sabotage is vacuous and was measured to happen even when written in good faith the same hour as the fix. `task cover-diff` (advisory: changed lines no test executed) and `task mutate-pkg PKG=...` (advisory mutation testing) mechanize the check — run them on touched packages and triage what they print.
- **Test the seam, not the halves.** The worst bug of the venue work — the launch rung never dialing the machine it acquired — sat between two well-tested units: the lease resolved a worker, the dialer parsed a URL, and no test carried the resolved worker ACROSS into the dial. When a feature's spine crosses a boundary (resolve→dial, capture→publish, parse→execute), the first test is the one that crosses it. A struct handed across a boundary as a string (URLs, paths) is the classic carrier of this bug.
- **A new error classification audits its consumers.** Adding a sentinel (an `ErrEvicted`) to an existing error chain means every consumer of the WRAPPED types re-decides: `errors.As` sees an `ExitError` straight through the new wrap, so a consumer that converts exit-to-data silently drops the classification. Grep every `errors.Is`/`errors.As`/type-assert on the wrapped types before calling the sentinel done.
- **Cleanup runs under its own context.** The likeliest reason a release/terminate/rollback path runs is that the caller's context was just cancelled — so a cleanup call using that context aborts before reaching the API and leaks the thing it was cleaning (measured: EC2 instances left billing). Give-back paths use `context.WithoutCancel` plus their own bound, and anything that acquires what costs money logs what it acquired, so a leak is at least findable.
- **Comments earn their place.** Write a comment only when it says something the code cannot: a why, a non-obvious invariant, an external constraint, a deliberate shortcut (`// ponytail:`). No restating the next line, no section banners, no narrating parameters. An extraneous comment is a defect — delete it rather than update it.

## Build, test, lint — `task` runs it all

Run `task` (bare — an alias for `task fmt`) after any code change. It is the whole sequence, in order, and needs no Docker or credentials; `Taskfile.yml` names each step and why it is there, govulncheck and nilaway are PINNED in `go.tool.mod` and run through `go tool` (nothing to install; `task upgrade:tools` moves them, and the diff is the upgrade), and `task --list` is the current inventory. What the Taskfile cannot tell you:

- **Lint must report `0 issues`** before a change is done — fix lint before touching logic further.
- **`task test` takes under two minutes, and `-race` covers every package but `./e2e`.** A data race is invisible to every other check here, and one shipped green through this whole sequence before the flag was added — but under `-race` the suite needs ~1,100 CPU-seconds, which ten cores cannot fit in two minutes however it is split, and `./e2e` is ~700 of them (pure-Go sqlite under the detector is ~15x). So `./e2e` runs without it, and **`task test:race` is its race sweep**: `task` prints one line when it has not passed in 10 commits, and it has earned its keep (8b7d6bb, a daemon race only e2e reached). Big packages run as process shards, which isolate globals but not the docker daemon or the clock — [tools/testshard/CLAUDE.md](tools/testshard/CLAUDE.md).
- **A govulncheck finding is usually a Go *patch* version issue**, not this repo's code — `brew upgrade go` fixes more of them than an edit does. Must report 0.
- **`//kindswitch:ignore <reason>`** suppresses a deliberate tagless-switch omission; the reason is mandatory (a bare directive is ignored and the switch keeps reporting).

Advisory targets sit outside the sequence (`task --list` names them all; `cover-e2e`/`judge-e2e` and `fuzz` are the rarer ones): `task cover-diff [BASE=rev]` prints changed lines no test executed, and `task mutate-pkg PKG=./internal/foo` runs mutation testing over one package; triage what they print rather than gating on them. Mutation testing runs as a periodic sweep tracked by `tools/mutation-ledger.json`, and `task` ends on one line when a sweep is due — [tools/mutants/CLAUDE.md](tools/mutants/CLAUDE.md). The `aws://`/`gcp://` venues are the surfaces no emulator can test; real fixtures are `hack/aws-fixture.sh`/`hack/gcp-fixture.sh` — [internal/venue/CLAUDE.md](internal/venue/CLAUDE.md).

All of them always pass clean on a fresh checkout. If any fails, that is a real regression — do not work around it with `--no-verify`-style shortcuts or by skipping a step.

**A commit must be the tree `task` passed on, and git checks.** `task` ends by sealing the hash of the tree it validated. `pre-commit` accepts that tree or any slice of it (a series of commits) while the working tree is unchanged; `pre-push` requires the pushed tip to be exactly that tree. When commit refuses: rerun `task`. When push refuses with a `D` line: commit the file it names. A Claude Code hook denies `--no-verify`, `git commit -n` and `core.hooksPath`. Mechanics and reasoning: [tools/stamp/CLAUDE.md](tools/stamp/CLAUDE.md).

**nilaway is a gate, and a false positive costs a sentence.** It was advisory behind `|| true` until 2026-09-18, and advisory-and-ignored is how 17 findings sat in a green tree. Read each finding and decide real bug vs. false positive — the known FP shapes are a nil slice indexed under a `len` guard, a comma-ok map read, and two values an invariant keeps in step. Prefer a guard the analyzer can SEE when one costs nothing (test the pointer about to be dereferenced, not its sibling; hand the checked value across rather than re-deriving it); otherwise suppress where it is reported with `//nolint:nilaway // <why the flow cannot happen>` — on the line, or on the line ABOVE when the line opens a block, which is the one placement the trailing form silently misses. A finding reported inside a callee cannot be suppressed from the caller, which is the analyzer saying the guard belongs in the code. `task nilaway` shows just this output.

**Test suite specifics:**
- Every package that spawns a goroutine has a `goleak` `TestMain` (`go.uber.org/goleak`; `grep -rl VerifyTestMain` lists them — usually `goleak_test.go`, Postgres's in `main_test.go` beside the server it starts, mcp's in `stdio_test.go`) — `go test ./...` fails if a test leaves a goroutine running. Three deliberate exceptions, each re-verified at the version its comment names: regexp2's `runClock` (`internal/web`, `./e2e`) is bounded rather than leaked; go-sdk's server-side `streamableServerConn.Read` (the six packages that serve MCP; an isolated pass does not clear it — [internal/mcp/CLAUDE.md](internal/mcp/CLAUDE.md)); and the cloud SDKs' connection pools are ignored only while the real-AWS/GCP tests run. A new package that spawns a goroutine in production code needs the same `TestMain` (copy an existing `goleak_test.go`, adjust the doc comment).
- **Docker-backed tests run whenever a daemon is reachable** and skip cleanly when not — a test guarding a shipped feature does not get to be optional. Use `internal/testdocker` (`Require`, plus `MountableDir` for bind mounts); the opt-in env vars for non-docker suites are listed there — [internal/testdocker/CLAUDE.md](internal/testdocker/CLAUDE.md). Otherwise `go test ./...` needs no network and no credentials.
- **Postgres-backed tests do not use docker**: `internal/testpostgres` runs a Postgres 17 from embedded-postgres' binaries, downloaded once into `~/.embedded-postgres-go` (so the first run on a machine needs the network), and skips cleanly if they cannot be had — [internal/testpostgres/CLAUDE.md](internal/testpostgres/CLAUDE.md).
- `go test ./... -run TestName` runs a single test; every package's tests also pass individually.
- No test requires an LLM API key or a live model — `internal/agent`'s conversation loop is tested against a fake/mock provider seam, not a real model.
- **A config field either moves the cache key or is named as not meant to** (`internal/merkle/keyfields_test.go`); leaving one out costs a "Never hashed: <why>" sentence on the field — [internal/merkle/CLAUDE.md](internal/merkle/CLAUDE.md).
- **Doc examples are tests, guarded by mutation testing.** Adding a `config.Step` field costs a schema property, a doc example, an assertion that example can fail on, and a mutation operator (or a written reason in `stepMutationSkips`); any other config type costs the first two. **End-to-end tests live in `./e2e`** (`e2e/e2e_test.go`, harness in `e2e/fakeprovider_test.go`) and must stay in ONE package there — only `cli.Run` spans the whole stack, and `task test` runs that one package as `tools/testshard` shards rather than as a second package `go test ./...` would schedule on its own. Mechanics for both: the `steps-tests` skill.

## Project layout

`main.go` is the process boundary and nothing else — it hands `os.Args` to `internal/cli` and turns the error back into an exit code. `internal/cli` is the kong-based command surface over single-responsibility `internal/` packages forming an **acyclic dependency graph**, enforced by `.golangci.yml`'s `depguard` linter (each package has an explicit import allow-list — a new import outside a package's list is a signal the change belongs elsewhere, not a rule to route around). `.golangci.yml` is where to read the graph, not a copy that can drift.

- **The state database is a contract and two drivers**: `internal/store` is stdlib-only, a consumer declares the facets it calls, only `internal/cli` names a driver (sqlite or Postgres), and `storetest` is the conformance suite both pass — [internal/store/CLAUDE.md](internal/store/CLAUDE.md).
- **Two front ends, one model**: [internal/web](internal/web/CLAUDE.md) serves the browser UI; [internal/events](internal/events/CLAUDE.md) is the stdlib-only leaf carrying run events to it.
- Other per-package guides: [internal/config](internal/config/CLAUDE.md), [internal/cli](internal/cli/CLAUDE.md), [internal/dockerapi](internal/dockerapi/CLAUDE.md), [internal/shell](internal/shell/CLAUDE.md), [internal/venue](internal/venue/CLAUDE.md), [internal/merkle](internal/merkle/CLAUDE.md), [internal/mcp](internal/mcp/CLAUDE.md), [internal/testdocker](internal/testdocker/CLAUDE.md).
- `tools/` holds build-time checkers, not shipped code: [tools/kindswitch](tools/kindswitch/CLAUDE.md) (the `go/analysis` pass), `tools/coverdiff` (`task cover-diff`), [tools/testshard](tools/testshard/CLAUDE.md), [tools/mutants](tools/mutants/CLAUDE.md) (`mutate-*`, `judge-e2e`), `tools/coverattr` (`task cover-e2e`), [tools/stamp](tools/stamp/CLAUDE.md) (the commit gate), and `tools/sqlscope`, whose test holds every query in `internal/store/sqlite` to naming its pipeline — it lives in `tools/` because depguard keeps `go/ast` out of that package's tests.

`README.md` has the quick-start; `PRODUCT.md` is a product-framing doc, not engineering reference. `examples/` holds the capstone pipelines (`pr-review.yml`, EXECUTED by `e2e/e2e_pr_review_test.go`; `self-build.yml` and `release.yml`, validated by `steps validate` only) and `examples/invalid/` (pipelines that must FAIL to load, each naming its error); the rest of the runnable example corpus moved into `docs/` — see [examples/CLAUDE.md](examples/CLAUDE.md).

**`docs/*.md` is the feature-by-feature reference AND the tested example corpus.** `docs/docs.go` makes the directory a Go package (`go:embed *.md` + fenced-block extraction, stdlib-only — rendering lives in the consumers: `steps docs` uses glamour in main, the web UI's `/docs` uses goldmark in `internal/web`). Every fenced ```yaml block is a complete pipeline that `e2e/docs_test.go` (same package as the e2e tests, for the same reason) schema-validates, runs through full `steps validate`, and — unless the fence says `noexec` (validate-only) or `fragment` (prose) — executes via `cli.Run(["test", ...])`. Agent examples carry `test=<id>` in the fence info, naming a scripted fake-LLM scenario in `docs_scenarios_test.go`; the harness rewrites `source:` to the fake endpoint so the rendered YAML stays clean. Pages are indexed by [docs/README.md](docs/README.md) (`TestDocsPagesListed` keeps the index complete). Proposals are GitHub issues, not pages — `docs/` describes what steps does today.

**Any DSL change requires a docs update, and the build enforces it from several directions**: `TestDocsCoverage` asserts every yaml tag of every config type appears — *in the right position* — in at least one tested doc block (add an example to the relevant page, not an exception), `TestSchemaKeysMatchStructs` holds the same tags against `steps.schema.json` in both directions, and the mutation suites above require a `config.Step` field to be breakable. A new field lands with a schema entry AND a doc example, or the build is red. `steps.schema.json` is the published, hand-written JSON Schema; `e2e/schema_test.go` asserts every example validates against it AND each `$defs` entry's properties equal its config struct's yaml tags by reflection (`schemaDefsByType`, plus the document root against `config.Config`).
