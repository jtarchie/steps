# CLAUDE.md: steps Pipeline Runner

Trust these instructions. Only search the codebase if something here is missing or turns out to be wrong — this file is validated, not guessed.

## What this repo is

**steps** is a Go CLI that executes Concourse-style YAML pipelines (`resource_types`/`resources`/`jobs`), with an LLM `agent` step type built in alongside conventional `get`/`task`/`put` steps. Resources are discovered/fetched via templated shell commands (or MCP); `agent` steps call an LLM with tool calling. All state is cached in SQLite (WAL mode) via content-addressed (merkle) hashing, so unchanged steps are skipped on rerun.

- **The state database is bounded, and both bounds are pipeline settings.** `defaults.version_history:` caps recorded resource versions per resource; `defaults.run_history:` caps runs per job, and reaping a run takes its events, per-step records, agent usage, placements and transcripts with it (`internal/store/retention.go`, called at the end of every build from `pipeline.RunJob`). Zero means no limit for both, per the convention in [docs/attempts-timeout.md](docs/attempts-timeout.md#zero-means-no-limit). `internal/store/footprint_test.go` MEASURES the result with sqlite's `dbstat` — a change that grows what a build costs on disk fails there, which is the point.
- **History is bounded by recency; the CACHE is bounded by count, never by age.** `nodes` and `job_runs` are the merkle/chain caches, capped as a multiple of `run_history:` and evicted newest-by-`rowid`. Age is the wrong question for them and was a real bug: a fully-cached poll records no new node, never reaches `recordChainSucceeded`, and publishes its skip events with an EMPTY hash (`reportChainSkipped`), so nothing about a cache HIT refreshes any timestamp — a working pipeline's entries just looked older every poll until an age-based floor swept past them, and the faster it polled the sooner it lost the cache. A count cap cannot do that: a fully-cached pipeline creates no new entries, so nothing is ever evicted.
- **Stored timestamps use `sortableNano`, not `time.RFC3339Nano`.** These columns are ordered and compared as TEXT, and RFC3339Nano TRIMS trailing zeros — so `…:00.5Z` sorts after `…:00.51Z`, and a whole second sorts after every fraction inside it. Retention DELETES by that order, which made it able to reap the newer of two runs in one second. Any new stored timestamp uses the fixed-width layout.
- **A state file may hold SEVERAL pipelines, and every row says which one it belongs to.** `--state <path>` overrides the default `.steps/<filename>.db`, so `steps web app.yml infra.yml --state shared.db` is one file; `--name <name>=<path>` overrides a pipeline's identity in it, which defaults to the YAML's base name (and is the same string as the web UI's `/p/<slug>/`). Sharing is a STORAGE decision and never a semantic one: `pipelines(id, name, path)` is the parent, every pipeline-scoped table carries `pipeline_id … REFERENCES pipelines(id) ON DELETE CASCADE`, and **the `Store` handle holds the id** — which is why ~60 methods kept their signatures and why a caller cannot forget to scope. The run-scoped tables (`run_steps`, `run_events`, `agent_usage`) reach it through `runs` instead, and `run_placements` reaches it that way too while also carrying a `pipeline_id` of its own, because the node it names is a composite reference into `nodes(pipeline_id, hash)`; `node_content` is deliberately global, keyed by a hash OF the content, so its sweep must stay pipeline-blind or the `RESTRICT` fires. **A new query in `internal/store` without a `pipeline_id` predicate is a bug**, and the sharpest case is the cache: `merkle.HashNode` folds in kind/content/parent but NOT the pipeline, so two pipelines each with a job named `build` over an identical task produce the same hash — unscoped, the second silently skips work it never did. That is why `nodes` is keyed `(pipeline_id, hash)` and `job_runs` `(pipeline_id, job_name, root_hash)`.
- **One `steps` process per state database, and nothing enforces it.** The `flock`-based single-watcher lock was deleted deliberately (2026-08-23), and `steps watch` itself was deleted in the CLI consolidation (2026-08-30, #89): `steps web` is the whole long-running mode — it serves, polls, and drains the queue both of those fill, and a second one against the same state file is a deployment mistake rather than a supported pairing. What the lock protected is `ResetStaleRunning`, which reads every `running` queue row as an abandoned leftover — true only when nothing else is alive, false when another process is mid-build, where flipping the row lets the job be claimed twice and silently defeats `serial:`/`max_in_flight`. With one daemon there is nothing to pair with, so `web` always owns the queue and always recovers; `--no-watch` went with it, and `--read-only` is unrelated (it withholds the HTTP controls, never the drain). Do not reintroduce a lock, or a second daemon, without asking.
- **There is no migration path, deliberately — but a mismatch is REFUSED, not ignored.** The schema is `CREATE TABLE IF NOT EXISTS` and nothing rewrites an older database: pre-production, a schema change means deleting the pipeline's `.steps/<filename>.db`, not an upgrade step. Do not add ALTER-based migration machinery back (a previous `addedColumns`/`rebuiltTables` pass was removed for this reason); if that ever changes, add a real version counter with ordered steps, not another table-shaped special case. **`schemaVersion` (stamped into `PRAGMA user_version`, checked by `checkSchemaVersion` at open) must be bumped by any DDL change an existing file cannot satisfy.** It is a detector, not a migration counter: without it an older database opened fine, lacked a column, failed every INSERT naming it — and since the run-event sink only *warns*, the build went GREEN having recorded nothing. An empty older database is stamped rather than refused, having nothing to lose.

- **Containers are created over the engine API, not by spawning `docker`.** `internal/dockerapi` is the ONLY package that holds an engine client, and it is a leaf (`internal/shell` imports it; nothing else does). It exists because a CLI answers two questions a library does not, and both fail TOTALLY rather than partially when unanswered: WHICH DAEMON — `client.FromEnv` reads `DOCKER_HOST` and stops, while docker goes on to `DOCKER_CONTEXT`, then the `currentContext` in `config.json`, then the store under `contexts/meta/<sha256 of the name>`, which is what `docker context use colima` writes and how a great many machines are configured; and WHICH CREDENTIALS — the daemon cannot read the operator's keychain, so the client resolves a login (`credHelpers`, then `credsStore`, then `auths`, with Docker Hub filed under a legacy v1 URL) and sends it on the request, without which every pull from a private registry 401s on a machine where `docker pull` works. **A new call that needs either answer goes through `dockerapi`, never through `client.FromEnv`.** Two consequences worth knowing: nothing needs a `docker` binary on PATH any more (a daemonless, docker-less orchestrator runs PLACED containerized steps fine, which is why `ValidateDockerCLI` is gone), and an `ssh://` `DOCKER_HOST` is REFUSED rather than dialled — not because ssh is hard, but because a remote daemon resolves a bind mount against its own filesystem, finds nothing, and creates an empty directory instead of failing; `--worker ssh://...` is the mechanism that actually sends the tree.
- **A container's exit status is DATA; only "there was no container" is an error.** The pipeline separates the step saying no from the machinery breaking by asking `shell.IsExitError`, and every answer used to come from `*exec.ExitError`, which has no constructor and can only describe a child of this process. Three outcomes must keep their meanings: a command that ran and exited nonzero is a `*shell.ExitError`; a DAEMON refusing the start (an unknown image) keeps the **125** `docker run` reports, because docs/infra.md documents that number and an agent is shown it as tool output; and a container that started and then DIED is neither — it never accepted a command, so it stays an infrastructure error, and misreading it lets a guard treat an unusable image as the guard answering no and skip the work it gates with nothing red. **A container that dies at birth is only detectable by WAITING** (`dockerapi.SettleFor`, `dockerSettleBound`): an image whose ENTRYPOINT swallows the keepalive is still running at the instant the start returns. The old shape got this for free because spawning `docker inspect` WAS the delay; asking directly is fast enough to ask too early.
- **No CI configured**: there is no `.github/`, no CONTRIBUTING.md. `Taskfile.yml` (go-task) is the entire validation pipeline — run it locally exactly as documented before considering any change done.

## Working rules

- **Unspecified behavior → ask "What would Concourse do?"** steps is a Concourse-shaped DSL; when a semantic isn't pinned down by this repo (what a field means at an edge, ordering, when a step is skipped, how a version is picked, what counts as a change), the default answer is whatever Concourse does. Research it thoroughly first — Concourse docs, its source, real pipeline behavior — then come back with the finding AND the open questions for the user. Do not invent a semantic and do not guess in silence; a divergence from Concourse is a deliberate decision the user makes, not a side effect of an implementation.
- **Foreign key constraints are required.** Every SQLite column in `internal/store` that references another table's key declares a `REFERENCES` constraint with an explicit `ON DELETE` action. `PRAGMA foreign_keys=ON` is set on the connection, so a missing constraint is a silently-orphaned row, not a saved line. A relationship that genuinely cannot be a foreign key needs a comment naming why. **Three columns are such exceptions, all pinned by a negative assertion in `footprint_test.go` so they stay deliberate**: `nodes.parent_hash`, because a container step (`do:`/`in_parallel:`/`race:`/`across:`/`ensemble:`/`try:`) records its node AFTER the children that hashed under it, so the child legitimately precedes the parent; and `job_runs.root_hash`, because a chain ending in a container has a leaf hash no node describes, and cascading the skip index off node retention would silently re-run work that succeeded; and `run_events.parent_step_id`, for the same shape of reason as `nodes.parent_hash`. Adding either of the first two makes every block step fail to record.
- **TDD, outside-in.** Write the test first. Start with the happy-path end-to-end test — the one that runs a real pipeline through `run()` and asserts the outcome a user would see — and only then work downward into the narrower tests (package-level, then unit) for the branches, errors, and edge cases the e2e pass doesn't reach. An e2e that passes is the proof the feature exists; the tests below it are the proof it holds up. A feature whose first test is a unit test is a feature nobody has run.
- **Fixes are features: they land with a test, and the test is proven by sabotage.** This rule exists because it was violated, expensively: a batch of review fixes landed test-free across several commits, and a later audit showed that deleting any of them shipped green through this whole sequence. Before committing a fix, break the fix (edit it back, in memory — never `git checkout --`, which also destroys the uncommitted fix), run the test, watch it fail, restore. A test that survives its own sabotage is vacuous and was measured to happen even when written in good faith the same hour as the fix. `task cover-diff` (advisory: changed lines no test executed) and `task mutate-pkg PKG=...` (advisory mutation testing) mechanize the check — run them on touched packages and triage what they print.
- **Test the seam, not the halves.** The worst bug of the venue work — the launch rung never dialing the machine it acquired — sat between two well-tested units: the lease resolved a worker, the dialer parsed a URL, and no test carried the resolved worker ACROSS into the dial. When a feature's spine crosses a boundary (resolve→dial, capture→publish, parse→execute), the first test is the one that crosses it. A struct handed across a boundary as a string (URLs, paths) is the classic carrier of this bug.
- **A new error classification audits its consumers.** Adding a sentinel (an `ErrEvicted`) to an existing error chain means every consumer of the WRAPPED types re-decides: `errors.As` sees an `ExitError` straight through the new wrap, so a consumer that converts exit-to-data silently drops the classification. Grep every `errors.Is`/`errors.As`/type-assert on the wrapped types before calling the sentinel done.
- **Cleanup runs under its own context.** The likeliest reason a release/terminate/rollback path runs is that the caller's context was just cancelled — so a cleanup call using that context aborts before reaching the API and leaks the thing it was cleaning (measured: EC2 instances left billing). Give-back paths use `context.WithoutCancel` plus their own bound, and anything that acquires what costs money logs what it acquired, so a leak is at least findable.
- **Comments earn their place.** Write a comment only when it says something the code cannot: a why, a non-obvious invariant, an external constraint, a deliberate shortcut (`// ponytail:`). No restating the next line, no section banners, no narrating parameters. An extraneous comment is a defect — delete it rather than update it.

## Build, test, lint — `task` runs it all

Run `task` (bare — an alias for `task fmt`) after any code change. It is the whole sequence, in order, and needs no Docker or credentials; `Taskfile.yml` names each step and why it is there, `task install:tools` installs the CLIs beyond the Go toolchain, and `task --list` is the current inventory. What the Taskfile cannot tell you:

- **Lint must report `0 issues`** before a change is done — fix lint before touching logic further.
- **`task test` runs `-race` and takes ~5.5 minutes.** Deliberate: a data race is invisible to every other check here, and one shipped green through this whole sequence before the flag was added. `-p 1` buys deterministic log interleaving, not correctness.
- **A govulncheck finding is usually a Go *patch* version issue**, not this repo's code — `brew upgrade go` fixes more of them than an edit does. Must report 0.
- **`//kindswitch:ignore <reason>`** suppresses a deliberate tagless-switch omission; the reason is mandatory (a bare directive is ignored and the switch keeps reporting).

Two advisory targets sit outside the sequence, run on demand when touching code (not docs): `task cover-diff [BASE=rev]` prints changed lines no test executed, and `task mutate-pkg PKG=./internal/foo` runs gremlins mutation testing over one package (minutes; hours for packages with heavy dependents like venue/pipeline — scope deliberately). Both exist because an untested layer once shipped green; triage what they print rather than gating on them. **The `aws://` and `gcp://` venues are the surfaces no emulator can test.** LocalStack, Moto and fakecloud all stop at the SSM control plane — none implements the session data channel, because it terminates at `amazon-ssm-agent` ON the instance and AWS has never specified it — and no emulator speaks the IAP relay protocol at all. `internal/venue/ssmdial` and `internal/venue/iapdial` are ports, and their fake-agent/fake-relay tests encode the same reading as each client, so a shared misreading passes both sides (iapdial's known instance: CONNECT_SUCCESS_SID is length-prefixed bytes, which two community Go clients misread as a uint64). `hack/aws-fixture.sh up` provisions a real AWS fixture (bucket, instance profile, launch template, one `t4g.small` (free only on an account created before 2025-07-15; otherwise it draws down signup credit), a FIS role) and prints the environment for the opt-in tests: protocol conformance (`./internal/venue/ssmdial`), transport and the acquisition rungs (`./internal/venue`), a pipeline end to end (`./e2e`), and a REAL spot reclamation via `aws:ec2:send-spot-instance-interruptions` — the only way to exercise IMDS → draining frame → re-placement. `hack/gcp-fixture.sh up` is the GCP mirror (firewall rule for the IAP range only, spot instance template with `DELETE`, one `e2-small`) feeding `STEPS_TEST_GCP_*` tests of the same shape, with `instances.simulateMaintenanceEvent` as the FIS stand-in — on a spot instance it IS a preemption, and whether the simulated path matches a real reclaim byte-for-byte is exactly what the fixture test verifies. Each `down` destroys everything its `up` made; the AWS security group has no inbound rules at all (the zero-inbound claim asserted by omission), while the GCP rule admits exactly `35.235.240.0/20 → 22` — the honest difference between the two transports.

All of them always pass clean on a fresh checkout (nilaway is advisory, so "clean" means golangci-lint/kindswitch/test/build/govulncheck are all clean — nilaway's own output is read, not gated on `task fmt`'s exit code). If any of the gating ones fails, that is a real regression — do not work around it with `--no-verify`-style shortcuts or by skipping a step.

**Every nilaway finding still gets triaged, gate or not** — "advisory" means it doesn't block a commit, not that a finding is presumed spurious. Read each one, decide real bug vs. false positive (Go's nil-slice-slicing pattern is the known FP shape), and fix the real ones — including ones a change didn't introduce. Advisory-and-ignored is how a real nil-flow bug sits in the tree indefinitely; the check exists precisely because these don't reliably show up any other way. `task nilaway` on its own is the fast way to see just this output when triaging.

**Test suite specifics:**
- Every package that spawns a goroutine (`internal/pipeline`, `internal/trigger`, `internal/web`, `internal/events`, `internal/agent`, `internal/mcp`, `internal/resource`, `internal/exprlang`, `internal/cli`, and `./e2e`) has a `goleak_test.go` `TestMain` (`go.uber.org/goleak`) — `go test ./...` fails if a test leaves a goroutine running. One known, deliberate exception: `goleak.IgnoreTopFunction("github.com/modelcontextprotocol/go-sdk/mcp.(*streamableServerConn).Read")` in those TestMains — the go-sdk's server-side streamable-HTTP read loop does not exit when a client sends the session-termination DELETE, verified in isolation against go-sdk@v1.7.0 both with and without the client's standalone SSE stream. Not steps' leak to fix; re-check when the SDK bumps past v1.7.0. A new package that spawns a goroutine in production code needs the same `TestMain` (copy an existing `goleak_test.go`, adjust the doc comment).
- **Docker-backed tests run whenever a daemon is reachable**, and skip cleanly when one is not — they are no longer opt-in. They were, behind `STEPS_TEST_DOCKER=1`, and that is exactly how a containerized placed step shipped NOT WORKING: `task` was green for hours because the only test covering the feature never ran, and a later refactor broke it in silence. A test that guards a shipped feature does not get to be optional. A test that BIND-MOUNTS needs a daemon-visible temp directory as well, because on macOS the daemon runs in a VM that does not share `/var/folders` and answers an unshared mount with an EMPTY directory — a step that then succeeds and produces nothing. `requireDockerE2E` does that for you (`daemonVisibleTemp`); `requireDocker`, `requireDockerAgent` and `requireDockerVenue` do not, so a bind-mounting test in those packages arranges it itself — and the helper is per package, not shared: `internal/shell` has `mountableTempDir` (`docker_integration_test.go`), `internal/agent` has `useSharedTempRoot` (`clicontainer_integration_test.go`), which points `TMPDIR` at the directory as well because the CLI it containerizes picks its own paths, and `internal/venue` has neither, so the first bind-mounting test there writes one. Still opt-in, because they are not docker-feature tests: `STEPS_TEST_BTRFS_ROOT=<dir>` (a real btrfs filesystem, Linux only) and `STEPS_TEST_BTRFS_DOCKER=1` (btrfs exercised through docker-as-a-Linux-VM — a ~1GB pull, apt-get over the network, a privileged container), plus the AWS fixture's own variables. Otherwise `go test ./...` needs no network and no credentials.
- `go test ./... -run TestName` runs a single test; every package's tests also pass individually.
- No test requires an LLM API key or a live model — `internal/agent`'s conversation loop is tested against a fake/mock provider seam, not a real model.
- **Doc examples are tests, guarded by mutation testing.** Adding a `config.Step` field costs a schema property, a doc example, an assertion that example can fail on, and a mutation operator (or a written reason in `stepMutationSkips`); any other config type costs the first two. **End-to-end tests live in `./e2e`** (`e2e/e2e_test.go`, harness in `e2e/fakeprovider_test.go`) and must stay in ONE package there — only `cli.Run` spans the whole stack, and a second e2e package would run concurrently with the first under `go test ./...`, where they contend for the docker daemon, ports and the shim binary. Mechanics for both: the `steps-tests` skill.

## Project layout

`main.go` is the process boundary and nothing else — it hands `os.Args` to `internal/cli` and turns the error back into an exit code. `internal/cli` is the kong-based command surface over single-responsibility `internal/` packages forming an **acyclic dependency graph**, enforced by `.golangci.yml`'s `depguard` linter (each package has an explicit import allow-list — a new import outside a package's list is a signal the change belongs elsewhere, not a rule to route around).

`internal/config` carries conventions the code alone won't teach — see [internal/config/CLAUDE.md](internal/config/CLAUDE.md), which loads when you work in that package.

**Two front ends, one model.** `internal/web` serves the browser UI and `internal/events` is the stdlib-only leaf carrying run events between them — see [internal/web/CLAUDE.md](internal/web/CLAUDE.md) and [internal/events/CLAUDE.md](internal/events/CLAUDE.md), which load when you work in those packages.

**`tools/`** holds build-time checkers, not shipped code — currently just `tools/kindswitch`, the `go/analysis` pass in the validation sequence above; see [tools/kindswitch/CLAUDE.md](tools/kindswitch/CLAUDE.md).

Config files: **`.golangci.yml`** (lint rules, and the `depguard` allow-lists that ARE the dependency graph — read it there rather than from a copy that can drift) — this *is* the pre-check-in validation pipeline, there's no separate CI file.

`README.md` has the quick-start; `PRODUCT.md` is a product-framing doc, not engineering reference. `examples/` now holds only `examples/pr-review.yml` (the live-model capstone example — statically validated by `TestValidatePRReviewExample`, and EXECUTED as written by `e2e/e2e_pr_review_test.go` against a scripted provider with `gh`/`git` stubbed on PATH) and `examples/invalid/` (pipelines that must FAIL to load, each naming its error — `e2e/examples_invalid_test.go`); the rest of the runnable example corpus moved into `docs/` — see [examples/CLAUDE.md](examples/CLAUDE.md).

**`docs/*.md` is the feature-by-feature reference AND the tested example corpus.** `docs/docs.go` makes the directory a Go package (`go:embed *.md` + fenced-block extraction, stdlib-only — rendering lives in the consumers: `steps docs` uses glamour in main, the web UI's `/docs` uses goldmark in `internal/web`). Every fenced ```yaml block is a complete pipeline that `e2e/docs_test.go` (same package as the e2e tests, for the same reason) schema-validates, runs through full `steps validate`, and — unless the fence says `noexec` (validate-only) or `fragment` (prose) — executes via `cli.Run(["test", ...])`. Agent examples carry `test=<id>` in the fence info, naming a scripted fake-LLM scenario in `docs_scenarios_test.go`; the harness rewrites `source:` to the fake endpoint so the rendered YAML stays clean. Pages are indexed by [docs/README.md](docs/README.md) (`TestDocsPagesListed` keeps the index complete). Proposals are GitHub issues, not pages — `docs/` describes what steps does today.

**Any DSL change requires a docs update, and the build enforces it from several directions**: `TestDocsCoverage` asserts every yaml tag of every config type appears — *in the right position* — in at least one tested doc block (add an example to the relevant page, not an exception), `TestSchemaKeysMatchStructs` holds the same tags against `steps.schema.json` in both directions, and the mutation suites above require a `config.Step` field to be breakable. A new field lands with a schema entry AND a doc example, or the build is red.

`steps.schema.json` is the published JSON Schema for the pipeline format, hand-written and kept honest by `e2e/schema_test.go` — which asserts every example validates against it AND that each `$defs` entry's properties equal the corresponding config struct's yaml tags by reflection (`schemaDefsByType`, plus the document root against `config.Config`). **Adding a field to any of those structs therefore requires adding it to the schema**, or the build fails.
