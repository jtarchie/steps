# examples/

The runnable example corpus lives in `docs/*.md` — every fenced ```yaml block there is a complete pipeline, extracted and executed by `TestDocsExamples` in `./e2e` (see `e2e/docs_test.go`). This directory keeps the things that can't be doc blocks — pipelines that only mean something against a real model, a real repository, or real credentials:

**`pr-review.yml`** is the capstone example: the full adaptive PR-review pipeline (planner-decided matrix width, concurrent reviewer cells, collected outputs, synthesizer fan-in, human approval before posting), meant to be run against a real model and a real repo. Its *verdict* can never be a fixture — pass/fail depends on what the reviewers find — but the file itself is executed by `TestEndToEndPRReviewExample`: read from disk, every agent pointed at a scripted provider through the same `source:` seam the doc corpus uses, with `gh` and `git` stubbed on PATH so the resource type's real `check`/`in`/`out` text runs, and the `approval:` answered through `steps approve` from outside the run. `TestValidatePRReviewExample` still validates it statically (schema + full `steps validate`).

**The two kinds of assertion in it are split on purpose.** The `assert:` blocks in the YAML state what must hold on a REAL run — each agent WROTE the artifact it promised, the draft check printed what it prints — so they are worth something to someone running this against their own PR. What is only true of the fixture (which dimensions the planner chose, how many cells ran, which nodes recorded) is asserted in Go. There is deliberately **no** `assert.execution` on the job: the matrix width is decided by the planner at run time, so the step names are not knowable when the file is written.

**`invalid/*.yml` are pipelines that must FAIL `LoadConfig`**, each with a `# expect: <substring>` line naming the error it has to produce (`examples_invalid_test.go`). That is where a load-time rejection gets a readable file, rather than living only as an error-substring assertion in a Go test.

**`security-audit.yml`** runs somebody else's methodology over somebody else's pull request: it `get`s [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill) with the built-in `git` type and the PR with the same `gh`-backed type `pr-review.yml` uses, then executes the skill's six phases as PIPELINE STEPS rather than as one agent orchestrating its own sub-agents. The skill's prompts stay in the skill — delivered as `context_paths:` at the revision the get pinned — so this file does not go stale when the skill is updated; what lives here is only what each phase is FOR. Three of its properties are the reason it is worth reading: the skill's write-isolation requirement is satisfied by ordinary step isolation (each `across:` cell has its own workspace, enforced by the runner rather than asked of a model), its OS-sandbox requirement by `image:` + `network: none` + `container_limits:` on the hunters, and its two Node validators are `task:` steps with a `fix:` agent — a deterministic gate between two agent phases, which is what stops a malformed ledger from fanning out ten hunters over a plan nobody checked. Both matrix widths are decided at run time (recon writes the unit list, consolidation writes the candidate list), so like `pr-review.yml` it carries no `assert.execution`. `TestValidateSecurityAuditExample` pins schema + full `steps validate`; it can never be executed by the suite, since it fetches over the network, shells out to `node`, and wants a docker daemon.

**`self-build.yml` and `release.yml` are the other two capstones**, lifted from the author's own pipelines repo and run as written there: one draft PR per issue labeled `self-build` (opus planner → sonnet implementer → opus reviewer whose verdict routes back on `revise`), and the pipeline that releases steps itself (a `v*` tag → `task` as the gate → `approval:` → goreleaser as a `put`). Neither is executed by the suite — both need `claude`/`gh`/`goreleaser` on PATH and a repository to act on — and neither carries `assert:` beyond what the file already explains; `steps validate` is what keeps them loading. They are here because a reader asking "what does a real one look like" should find one in the repo, not in a blog post.
